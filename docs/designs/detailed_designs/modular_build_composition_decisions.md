# Decision Note: 모듈형 빌드 구성 1차 결정사항

## 문서 메타데이터

- 문서 일자: 2026-03-27
- 문서 유형: Decision Note
- 관련 설계: [./modular_build_composition_and_tool_specific_tasks.md](./modular_build_composition_and_tool_specific_tasks.md)

## 요약

모듈형 빌드 구성 설계를 실제 구현 가능한 수준으로 진행하기 위해 1차 기본 결정을 정리한다. 별도 반대 결정이 나오기 전까지는 본 문서를 기준으로 후속 구현 설계와 API 설계를 진행한다.

## 결정사항

### 1. 모듈 정의 파일 포맷은 1차적으로 YAML을 사용한다.

- 결정:
  - `stage`, `job`, `task` 선언형 파일은 YAML을 기본 포맷으로 사용한다.
- 이유:
  - 운영자가 직접 읽고 수정하기 쉽고, 주석과 멀티라인 스크립트 참조 메타데이터 표현이 편하다.

### 2. 자동 로딩은 관리 디렉터리 스캔 + 관리자 재로드 방식으로 시작한다.

- 결정:
  - 프로세스 시작 시 전체 스캔을 수행하고, 이후에는 관리자 재로드 액션으로 반영한다.
  - 파일 변경 감지 기반 hot reload는 1차 범위에서 제외한다.
- 이유:
  - 구현과 운영 통제가 단순하고, 부분 실패 시 복구 지점을 명확히 둘 수 있다.

### 3. 웹 업로드는 선언형 모듈과 스크립트 자산만 허용한다.

- 결정:
  - 웹 업로드 대상은 YAML 모듈 파일과 스크립트 템플릿 자산으로 제한한다.
  - Python provider/renderer/validator 코드 업로드는 허용하지 않는다.
- 이유:
  - 임의 코드 업로드는 보안과 배포 책임 경계를 흐린다.

### 4. 업로드 저장소는 1차적으로 서버 관리 디렉터리를 사용한다.

- 결정:
  - 업로드 자산은 서버의 관리 디렉터리에 저장하고, 메타데이터와 이력만 DB에서 관리한다.
- 이유:
  - 런타임 스캔 구조와 자연스럽게 연결되고 구현 복잡도가 낮다.

### 5. 모듈 로딩 실패는 전체 중단보다 부분 격리를 우선한다.

- 결정:
  - 오류가 있는 모듈은 `invalid` 상태로 격리하고, 유효한 모듈만 로딩한다.
  - 단, id 충돌처럼 전역 정합성을 깨는 오류는 해당 종류 로딩을 실패로 처리할 수 있다.
- 이유:
  - 운영 환경에서 하나의 잘못된 파일이 전체 시스템 가용성을 떨어뜨리는 것을 피하기 위함이다.

### 6. Python task의 Windows 기본 실행은 wrapper 우선으로 둔다.

- 결정:
  - Windows 대상 Python task는 `.py` 본문과 필요 시 `.bat` wrapper를 함께 생성하는 방향을 기본값으로 둔다.
- 이유:
  - 호출 방식 차이와 CI step 차이를 흡수하기 쉽고, Bamboo/Jenkins 양쪽에 연결하기 단순하다.

### 7. task 스키마는 provider별 디렉터리로 분리한다.

- 결정:
  - `modules/tasks/bamboo/`, `modules/tasks/jenkins/`처럼 provider별 경로를 분리한다.
- 이유:
  - 공통 추상화를 억지로 강제하지 않고 검증기와 렌더러를 명확히 연결할 수 있다.

## 후속 검토 필요 사항

- 업로드 승인 흐름을 단순 관리자 권한 즉시 반영으로 둘지 승인 단계까지 둘지 결정 필요
- YAML 스키마 버전 업 전략을 `apiVersion` 하나로 둘지 provider별 버전을 분리할지 결정 필요
- 모듈 로딩 상태를 DB snapshot으로 남길지 메모리 registry 상태만 유지할지 결정 필요
