# Decision Note: 다중 CI 콘솔 1차 결정사항

## 문서 메타데이터

- 문서 일자: 2026-03-25
- 문서 유형: Decision Note
- 관련 설계: [./multi_ci_console_and_provider_model.md](./multi_ci_console_and_provider_model.md)

## 요약

다중 CI 콘솔 확장을 진행하기 위해 1차로 확정하거나 기본값으로 채택한 결정사항을 정리한다. 구현 중 변경 가능하지만, 별도 반대 결정이 나오기 전까지는 본 문서를 기준으로 후속 설계를 진행한다.

## 결정사항

### 1. 상단 모드 전환은 URL 기반으로 관리한다.

- 결정:
  - 현재 provider 상태는 URL 세그먼트로 표현한다.
- 이유:
  - 새로고침, 북마크, 공유 링크, 서버 렌더링 템플릿 처리에 가장 단순하다.
- 예시:
  - `/ui/bamboo/projects/`
  - `/ui/jenkins/projects/`

### 2. 공통 추상어는 `BuildUnit`을 사용한다.

- 결정:
  - Bamboo `plan`과 Jenkins `job`을 감싸는 문서/설계상의 공통 용어로 `BuildUnit`을 사용한다.
- 이유:
  - `build`, `job`, `plan`은 각각 특정 도구 의미가 강하다.
  - `BuildUnit`은 UI/도메인/API에서 중립적이다.

### 3. 공통 필드와 도구별 필드는 분리한다.

- 결정:
  - 공통 응답에는 provider 무관 필드만 둔다.
  - 도구별 세부 속성은 `providerDetails`에 둔다.
- 이유:
  - 공통 UI와 API를 유지하면서 도구별 확장을 수용하기 쉽다.

### 4. Jenkins 등록 단위는 1차적으로 `job` 중심으로 둔다.

- 결정:
  - 1차 요구사항 기준 Jenkins 등록 핵심 단위는 `job`이다.
  - folder 계층은 식별 경로의 일부로 수용한다.
- 이유:
  - 요구사항의 핵심은 프로젝트와 빌드 잡 등록이며, folder 전체 관리까지 포함하면 범위가 과도하게 커진다.

### 5. 공통 UI 구조는 유지하고 테마만 provider별로 바꾼다.

- 결정:
  - Bamboo/Jenkins 전환 시 메뉴 구조와 정보 구조는 유지한다.
  - Bamboo는 밝은 파란색, Jenkins는 밝은 빨간색을 기본 테마로 사용한다.
- 이유:
  - 공통 운영 경험을 유지하면서도 현재 도구 인지를 돕기 위함이다.

### 6. 시스템 현황 화면은 provider별로 따로 구현하되 공통 레이아웃을 쓴다.

- 결정:
  - Bamboo는 agent 중심, Jenkins는 node/executor 중심 데이터를 사용한다.
  - 화면 레이아웃은 summary + resource table + queue 패널로 통일한다.
- 이유:
  - 데이터 의미는 다르지만 운영자가 기대하는 관측 화면 구조는 유사하다.

### 7. 기존 Bamboo 중심 구조는 호환 유지 없이 교체한다.

- 결정:
  - 기존 `BuildPlan` 중심 구조를 장기 호환 대상으로 보지 않는다.
  - 신규 구현은 `BuildUnit` 중심 공통 모델을 기준으로 다시 설계한다.
- 이유:
  - 기존 구조를 유지한 채 일반화하면 Bamboo 개념이 공통 코어에 계속 남는다.
  - 구조 전환 비용이 큰 만큼 중간 호환 계층을 최소화하는 편이 낫다.

### 8. 기존 데이터는 마이그레이션하지 않는다.

- 결정:
  - 기존 로컬/개발 데이터는 신규 구조로 이전하지 않아도 된다.
  - 필요 시 DB 초기화 후 JSON 재적재 또는 신규 등록으로 다시 채운다.
- 이유:
  - 현재 목적은 구조 재정의이며, 데이터 이관 비용이 설계와 구현을 방해한다.
  - 운영 전환 전 단계에서는 스키마 정합성이 데이터 연속성보다 우선이다.

## 후속 검토 필요 사항

- provider별 권한 분리 수준 결정 필요
- Jenkins job type을 freestyle/pipeline으로 명시 분리할지 결정 필요
