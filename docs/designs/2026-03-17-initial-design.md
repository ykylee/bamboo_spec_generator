# 초기 설계: Bamboo Specs 생성기

## 문서 메타데이터

- 문서 일자: 2026-03-17
- 문서 유형: Design
- 상태: 초안
- 관련 SRS: [2026-03-17-bamboo-spec-generator-srs.md](../requirements/2026-03-17-bamboo-spec-generator-srs.md)

## 요약

이 설계안은 Bamboo Specs 생성기의 초기 구조를 제안한다. 핵심 방향은 입력 파싱, 검증, 내부 모델 변환, 코드 생성, 산출물 저장을 분리하고, 여러 빌드 정의를 하나의 Bamboo Specs 프로젝트로 생성해 Bamboo가 단일 저장소만 스캔해 전체 플랜을 반영할 수 있게 하는 것이다.

## 배경

- 요구사항상 다중 JSON 입력과 연도별 관리가 필수다.
- 생성 대상은 하나의 Bamboo Specs 저장소 안에서 여러 플랜을 함께 관리할 수 있는 Java 산출물이어야 한다.
- 초기 설계 단계에서는 구현 난이도와 확장성을 함께 고려해야 한다.

## 목표

- MVP 구현이 가능한 최소 구조를 정의한다.
- 입력 구조와 출력 구조를 일관되게 정한다.
- 코드 생성 로직과 Base 코드 관리를 분리한다.
- 단일 Specs 저장소 기반 운영 모델을 반영한다.

## 비목표

- 최종 Java API 세부 구현 확정
- Bamboo 서버 반영 자동화 설계
- GUI 또는 웹 인터페이스 설계

## 설계안

### 1. 권장 저장소 구조

```text
.
├── docs/
│   ├── requirements/
│   └── designs/
├── build_info_json/
│   └── 2026/
│       ├── build-a.json
│       └── build-b.json
├── base/
│   └── bamboo-specs/
├── bamboo-specs/
│   └── src/main/java/com/example/specs/
└── src/
    ├── parser/
    ├── validator/
    ├── model/
    ├── generator/
    └── writer/
```

### 2. 처리 파이프라인

1. 입력 탐색기
   지정된 파일 또는 디렉터리에서 JSON 입력을 수집한다.
2. 파서
   JSON을 읽어 원시 입력 객체로 변환한다.
3. 검증기
   필수 필드, 형식, 중복 키를 검사한다.
4. 모델 변환기
   입력 객체를 Bamboo 플랜 생성용 내부 모델로 변환한다.
5. 코드 생성기
   내부 모델과 Base 코드를 이용해 Bamboo Specs Java 코드를 생성한다.
6. 산출물 기록기
   하나의 Bamboo Specs 프로젝트 구조 아래에 플랜별 Java 소스를 기록한다.
7. 결과 리포터
   성공/실패 요약과 산출물 경로를 출력한다.

### 3. 내부 모델 초안

- `BuildDefinition`
  - `year`
  - `buildId`
  - `planKey`
  - `name`
  - `language`
  - `compiler`
  - `requirements`
  - `buildConfig`
- `RequirementsDefinition`
  - `os`
  - `extraCapabilities`
- `BuildConfig`
  - `buildCommand`
  - `staticAnalysis`
  - `trigger`

이 모델은 MVP 기준 최소 구조이며, 스테이지 자체는 입력이 아니라 공통 워크플로우 템플릿으로 고정한다. 이후 트리거, 브랜치, 변수, 권한 등을 확장할 수 있다.

### 4. 입력 관리 전략

- 연도 정보는 연도별 디렉터리 구조를 기준으로 관리한다.
- JSON 내부에는 `year` 필드를 두지 않는다.
- 빌드 정보 JSON 파일 저장 루트는 `build_info_json/`를 사용한다.
- 입력 루트 예시는 `build_info_json/<year>/*.json` 형태를 권장한다.
- JSON은 스테이지 정의 전체를 포함하지 않고, 언어 및 컴파일러 환경에 따른 빌드 상세 정보만 담는다.

### 5. 공통 워크플로우 전략

- 모든 플랜은 동일한 공통 워크플로우를 사용한다.
- 스테이지 순서는 다음과 같이 고정한다.
  1. 빌드 준비
  2. 빌드
  3. 정적분석
  4. 후속 작업 트리거
- 정적분석 스테이지 내부에는 2개의 병렬 Job을 둔다.
- 정적분석 Job 1은 Coverity 실행을 담당한다.
- 정적분석 Job 2는 커스텀툴 실행을 담당하며 `analyze {build command}` 형태의 명령을 포함한다.
- JSON 입력은 이 공통 워크플로우 안에서 달라지는 빌드 상세 설정만 제공한다.
- ScriptTask에 전달하는 실제 명령은 가능하면 shell 전용 문법 대신 Python 스크립트 호출 형태로 구성해 Windows와 Linux 호환성을 높인다.
- 빌드가 포함된 Job에는 compiler와 OS 기반 requirement를 함께 설정한다.
- 프로젝트 특성에 따라 `cuda12.1`, `nuget` 같은 추가 capability requirement를 붙일 수 있다.

### 6. 산출물 관리 전략

- 출력 루트는 루트의 `bamboo-specs/`를 기본값으로 둔다.
- 여러 빌드 정의는 하나의 Bamboo Specs 프로젝트 안에 함께 생성한다.
- 빌드별 식별은 클래스명, 파일명, 패키지 구조 또는 보조 메타데이터로 유지한다.
- Bamboo는 이 단일 Specs 저장소를 스캔해 전체 플랜 변경을 반영하는 운영 모델을 사용한다.

### 7. Base 코드 관리 전략

- Base 코드는 `base/bamboo-specs/` 아래에 둔다.
- 원본 유지가 필요한 경우 `upstream/`와 `custom/`를 분리하는 방식을 권장한다.
- 생성기는 Base 코드 전체를 수정하기보다 템플릿, 참조 클래스, 조합 계층을 통해 활용하는 쪽이 유지보수에 유리하다.

### 8. 오류 처리 전략

- 기본 정책은 파일 단위 실패 격리다.
- 유효하지 않은 특정 JSON이 있어도 다른 유효한 입력 처리는 계속할 수 있게 설계하는 쪽이 운영상 유리하다.
- 다만 `--fail-fast` 같은 옵션을 두면 전체 중단 정책도 지원 가능하다.

## 대안

### 대안 1. JSON 내 메타데이터만으로 연도 관리

- 장점: 디렉터리 구조 제약이 약하다.
- 단점: 운영자가 저장소에서 연도별 파일을 한눈에 파악하기 어렵다.

### 대안 2. 빌드 전체를 단일 JSON 파일에 묶기

- 장점: 실행 단위가 단순해진다.
- 단점: 빌드 수가 많아질수록 병합 충돌과 변경 관리가 어려워진다.

### 대안 3. Base 코드 직접 수정 방식

- 장점: 초기 구현이 빠를 수 있다.
- 단점: 업스트림 변경 추적과 버전 관리가 어려워진다.

## 영향 범위

- 입력 파일 구조 표준 정의 필요
- 공통 워크플로우 템플릿 정의 필요
- 생성기 애플리케이션 구조 결정 필요
- Base 코드 저장 위치와 관리 정책 결정 필요
- 단일 Specs 저장소 반영 시 운영 배포 정책 정의 필요
- 향후 테스트 전략 수립 필요

## 수용 기준

- 입력, 검증, 모델, 생성, 출력 책임이 분리된 구조를 제안한다.
- 연도별 입력 관리와 단일 Specs 저장소 산출물 방식이 정의되어 있다.
- Base 코드 저장 위치와 활용 방향이 정의되어 있다.
- 구현 시작에 필요한 최소 디렉터리 및 컴포넌트 구조가 제시되어 있다.

## 오픈 이슈

- 구현 언어와 빌드 도구를 무엇으로 선택할지 결정 필요
- 템플릿 기반 생성과 AST/모델 기반 생성 중 어떤 방식을 택할지 결정 필요
- 최소 지원 Bamboo 구성 요소 범위 확정 필요
- 공통 워크플로우 각 스테이지의 세부 Task 구성을 어떤 수준까지 고정할지 결정 필요
- Base 코드 라이선스 확인 필요
- 단일 저장소 커밋이 여러 플랜에 동시에 영향을 줄 때 승인 또는 배포 절차를 어떻게 둘지 결정 필요
