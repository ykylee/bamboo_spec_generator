# 설계: 플랜 스크립트 자산 분리 및 환경별 커스터마이징

## 요약

이 문서는 Bamboo Specs 생성기에서 플랜 Task 스크립트를 코드 내부 문자열 중심 구조에서 별도 스크립트 자산 기반 구조로 전환하는 설계를 정의한다. 핵심 방향은 공통 스크립트와 환경별 차이를 분리하고, 저장소 내 평문 스크립트 파일을 기준 자산으로 관리하며, 생성 시점에 빌드 정의에 맞는 값과 조각을 결합해 최종 Task 스크립트를 만드는 것이다. 초기 구현은 `sh`, `bat`, `py` 파일을 중심으로 하며, 최종 Bamboo Specs 표현 방식은 당분간 inline body를 유지하되 자산 원본은 별도 파일로 관리한다.

## 배경

- 현재 생성기는 여러 Task 스크립트를 Python 코드 내부 문자열로 직접 생성한다.
- 이 구조는 공통 로직 재사용, 스크립트 자체 검토, 언어별 편집 편의성 측면에서 한계가 있다.
- 플랜별 차이는 대부분 OS, 셸, 컴파일러, 작업 경로, 명령어 값에 집중되므로 공통 자산과 변수 분리 방식이 적합하다.
- 운영 관점에서는 공통 스크립트 일부를 수정했을 때 어떤 플랜 생성 결과에 영향을 주는지 추적 가능한 구조가 필요하다.

## 목표

- 스크립트 자산을 저장소 내 별도 파일로 관리한다.
- 공통 로직과 환경별 차이를 조합 가능한 구조로 분리한다.
- 생성 시점에 빌드 정의를 바탕으로 최종 스크립트를 결정론적으로 만든다.
- 언어별 스크립트 파일을 사람이 직접 읽고 수정하기 쉬운 구조로 둔다.
- 기존 생성 흐름을 한 번에 깨지 않고 단계적으로 전환 가능하게 한다.

## 비목표

- 첫 단계에서 모든 스크립트 언어를 지원하지 않는다.
- Bamboo 서버에 스크립트 파일만 독립 배포하는 메커니즘은 설계하지 않는다.
- 범용 템플릿 엔진 도입 자체를 목표로 두지 않는다.

## 설계안

### 1. 자산 디렉터리 구조

스크립트 자산은 생성기 코드와 분리된 전용 디렉터리에서 관리한다.

```text
scripts/
└── plan_tasks/
    ├── common/
    │   ├── py/
    │   │   ├── prepare_build.py
    │   │   ├── run_build.py
    │   │   ├── run_coverity.py
    │   │   └── trigger_follow_up.py
    │   ├── sh/
    │   └── bat/
    ├── overlays/
    │   ├── linux/
    │   ├── windows/
    │   ├── compiler/
    │   │   ├── maven/
    │   │   └── vs2022/
    │   └── task/
    │       ├── prepare/
    │       ├── build/
    │       ├── coverity/
    │       └── custom_analysis/
    └── fragments/
        ├── py/
        ├── sh/
        └── bat/
```

- `common/`은 Task별 기본 스크립트 원본을 둔다.
- `overlays/`는 OS, compiler, Task 특화 보정 내용을 둔다.
- `fragments/`는 여러 스크립트에서 재사용되는 공통 조각을 둔다.
- 초기 구현에서는 모든 디렉터리를 동시에 채울 필요는 없고, 실제 필요한 자산부터 추가한다.

### 2. 스크립트 자산 단위

스크립트 자산은 다음 메타 속성을 가진다.

- `task_name`
  - 예: `prepare`, `build`, `coverity`, `custom_analysis`, `trigger_follow_up`
- `script_language`
  - 예: `py`, `sh`, `bat`
- `target_os`
  - 예: `linux`, `windows`, `any`
- `compiler_scope`
  - 예: `any`, `maven`, `vs2022`

실제 파일명은 사람이 쉽게 찾을 수 있는 규칙을 우선한다.

예:

- `common/py/prepare_build.py`
- `overlays/windows/bat/build_env_setup.bat`
- `overlays/compiler/vs2022/py/msbuild_env.py`

### 3. 생성 입력 모델 확장

기존 `BuildDefinition`만으로도 1차 구현은 가능하지만, 명시적 모델이 있으면 생성 규칙이 단순해진다. 내부적으로 다음 구조를 추가한다.

- `ScriptAssetReference`
  - `task_name`
  - `script_language`
  - `base_asset_path`
  - `overlay_asset_paths`
- `ScriptRenderContext`
  - `build_id`
  - `os`
  - `compiler`
  - `sub_path`
  - `prepare_command`
  - `build_command`
  - `custom_tool_commands`
  - `target_plan_key`
  - `environment_variables`

1차 단계에서는 이 모델을 JSON 입력에 직접 노출하지 않고 생성기 내부 계산값으로 둔다. 이후 필요하면 JSON에 script profile 같은 선택 필드를 추가할 수 있다.

### 4. 렌더링 방식

초기 버전은 복잡한 외부 템플릿 엔진 대신 단순 문자열 치환과 조각 결합 방식을 사용한다.

예시 플레이스홀더:

- `{{BUILD_ID}}`
- `{{SUB_PATH}}`
- `{{PREPARE_COMMAND}}`
- `{{BUILD_COMMAND}}`
- `{{TARGET_PLAN_KEY}}`
- `{{PYTHON_COMMAND}}`

렌더링 순서는 다음과 같다.

1. Task와 빌드 환경에 맞는 기본 자산 선택
2. OS/컴파일러/Task 오버레이 목록 계산
3. 공통 조각과 오버레이 조각 결합
4. 플레이스홀더 값 치환
5. 최종 스크립트 정규화
6. Bamboo Specs 생성 로직에 전달

정규화 단계에서는 다음을 수행한다.

- 줄바꿈 형식 고정
- trailing whitespace 제거
- 필요 시 `subPath` 기준 경로 표현 반영
- 언어별 escaping 최소화

### 5. Task 언어 선택 규칙

Task는 본질적으로 하나의 최종 스크립트 언어를 가진다. 선택 규칙은 다음 우선순위를 따른다.

1. OS 고정 규칙
   - `windows`면 기본적으로 `bat`
   - `linux`면 기본적으로 `sh`
2. 공통 제어 스크립트 예외
   - 여러 환경에서 재사용성이 큰 제어 로직은 `py`를 우선 고려한다.
3. compiler 특화 예외
   - 예를 들어 `vs2022` 환경은 `bat` 기반 환경 로드 후 `py` 호출을 결합할 수 있다.

즉 최종 Task는 단일 언어만 쓴다기보다, 상위 진입 스크립트와 보조 호출 스크립트가 조합될 수 있다. 다만 자산 관리는 각 언어 파일 단위로 분리한다.

### 6. 공통부와 환경별 차이 분리 방식

공통부와 환경별 차이는 다음 기준으로 나눈다.

- 공통부
  - 로깅 형식
  - 작업 디렉터리 계산 골격
  - 명령 실행 wrapper
  - 오류 처리 패턴
  - 공통 helper 함수
- 환경별 차이
  - 셸 문법
  - 경로 구분자
  - Visual Studio 환경 로드
  - compiler별 명령 프리셋
  - Task별 실제 실행 명령

가장 중요한 원칙은 "환경별 차이를 공통 스크립트 안의 조건문으로 과도하게 밀어 넣지 않는다"는 점이다. 가능하면 base + overlay 조합으로 분리하고, 하나의 파일 안에 다수 환경 분기를 쌓지 않는다.

### 7. 최종 Bamboo Specs 반영 방식

초기 단계에서는 Bamboo Specs 결과물의 표현 방식은 유지한다.

- 자산 원본은 저장소 내 파일로 관리
- 생성 시 최종 스크립트 문자열을 렌더링
- 렌더링된 결과를 현재와 같이 Java `ScriptTask.inlineBody(...)` 또는 동등한 방식에 반영

이 접근의 장점은 다음과 같다.

- 현재 출력 구조와 큰 충돌이 없다.
- Bamboo 실행 모델을 바꾸지 않고 자산 관리 구조만 개선할 수 있다.
- 향후 파일 기반 배포로 전환하더라도 자산 구조를 재사용할 수 있다.

후속 단계에서는 생성 산출물 안에 실제 스크립트 파일을 함께 두고 Java 코드가 이를 참조하도록 바꾸는 방안도 검토한다.

### 8. 생성기 구조 변경

현재 `generator.py`가 직접 스크립트 본문을 조립하는 구조는 다음 책임으로 나눈다.

1. `script_assets.py`
   - 자산 탐색
   - 자산 선택 규칙
2. `script_renderer.py`
   - 플레이스홀더 치환
   - 오버레이 결합
   - 정규화
3. `generator.py`
   - 렌더링된 최종 스크립트를 Java 코드에 주입

이 구조를 사용하면 `generator.py`는 "어떤 문자열을 쓸지 계산"보다 "생성된 문자열을 어디에 반영할지 결정"에 집중할 수 있다.

### 9. 검증 규칙

자산 기반 구조에는 기존 입력 검증 외 추가 검증이 필요하다.

- Task별 기본 자산 파일이 존재해야 한다.
- 선택된 스크립트 언어와 파일 확장자가 일치해야 한다.
- 필수 플레이스홀더가 모두 치환되어야 한다.
- 사용되지 않은 미치환 플레이스홀더가 남으면 오류로 처리해야 한다.
- OS/compiler 조합에 필요한 오버레이가 정의돼야 하는 경우 누락 시 오류를 반환해야 한다.

### 10. 테스트 전략

테스트는 세 층으로 나눈다.

1. 자산 선택 테스트
   - 입력 OS와 compiler에 따라 올바른 base/overlay가 선택되는지 검증
2. 렌더링 테스트
   - 플레이스홀더 치환과 줄바꿈 정규화 결과 검증
3. 통합 생성 테스트
   - 최종 Java 산출물에 기대 스크립트 본문이 반영되는지 검증

가능하면 언어별 스냅샷 테스트를 도입해 diff 기반 검토가 가능하도록 한다.

### 11. 전환 전략

현재 inline script 생성 구조를 한 번에 제거하지 않는다.

1. 스크립트 자산 디렉터리 도입
2. 기존 Python 기반 스크립트부터 자산 파일로 분리
3. 생성기는 자산 렌더링 결과를 inline body에 주입
4. Windows 전용 배치 자산과 Linux 셸 자산 확장
5. 필요 시 출력물 내 파일 동반 생성 구조 검토

이 순서를 따르면 기존 README와 테스트를 크게 깨지 않고 점진 전환이 가능하다.

## 대안

### 대안 1. 현재처럼 코드 내부 문자열 유지

- 장점: 구현 변경 범위가 작다.
- 단점: 공통 스크립트 재사용, 코드리뷰, 언어별 편집성이 계속 나쁘다.

### 대안 2. 범용 템플릿 엔진 즉시 도입

- 장점: 조건문, 반복문, 조합 표현력이 높다.
- 단점: 초기 복잡도가 커지고 템플릿 자체 디버깅 비용이 늘어난다.

### 대안 3. 생성 산출물에 실제 스크립트 파일만 두고 Java 코드에서는 파일 참조

- 장점: 스크립트 자산과 생성 산출물의 형태가 유사해진다.
- 단점: 현재 Bamboo Specs 표현 방식과의 정합성 검토가 추가로 필요하다.

## 영향 범위

- 스크립트 자산 디렉터리 추가
- 생성기 모듈 구조 변경
- 테스트 구조 확장
- 샘플 입력과 생성 결과 검증 방식 조정
- README 및 운영 문서 갱신 필요

## 수용 기준

- 스크립트 자산 디렉터리 구조가 정의되어 있다.
- 공통 자산과 환경별 오버레이를 분리하는 규칙이 정의되어 있다.
- `sh`, `bat`, `py` 파일 관리 방식이 문서화되어 있다.
- 생성 시점 렌더링과 Bamboo Specs 반영 흐름이 정의되어 있다.
- 현재 구조에서 신규 구조로의 점진 전환 방안이 제시되어 있다.

## 오픈 이슈

- 장기적으로 inline body를 유지할지 파일 참조 방식으로 전환할지 결정 필요
- 오버레이 우선순위를 OS, compiler, task 중 어떤 순서로 고정할지 확정 필요
- 플레이스홀더 문법을 단순 치환으로 제한할지 최소 조건 분기를 허용할지 결정 필요
- 스크립트 자산 버전과 생성기 버전을 별도로 관리할 필요가 있는지 검토 필요
