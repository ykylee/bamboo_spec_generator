# 구현 계획: 플랜 스크립트 자산 분리 및 환경별 커스터마이징

## 요약

이 문서는 플랜 스크립트 자산 분리 설계를 실제 구현으로 옮기기 위한 단계별 계획을 정리한다. 핵심 원칙은 현재 동작을 최대한 유지하면서 스크립트 원본 관리 구조를 먼저 분리하고, 이후 렌더링 로직과 검증 로직을 추가해 점진적으로 전환하는 것이다.

## 구현 원칙

- 기존 생성 결과를 한 번에 바꾸지 않는다.
- 현재 테스트를 유지한 상태에서 단계별로 구조를 분리한다.
- 자산 원본 파일 도입과 렌더링 로직 도입을 분리한다.
- 초기에는 Python 기반 스크립트를 우선 이관하고, 이후 `bat`, `sh` 자산을 확장한다.
- 최종 Bamboo Specs 반영 방식은 초기 단계에서 inline body를 유지한다.

## 단계별 계획

### 1. 자산 구조 스캐폴딩

목표:
- 저장소에 스크립트 자산 디렉터리 구조를 도입한다.

작업:
- `scripts/plan_tasks/common/py/` 디렉터리 추가
- 필요 시 `scripts/plan_tasks/common/bat/`, `scripts/plan_tasks/common/sh/` 디렉터리 추가
- 후속 확장을 위한 `overlays/`, `fragments/` 디렉터리 추가
- 현재 `generator.py` 내부에 있는 Python 스크립트 내용을 별도 파일로 옮길 대상 목록 정리

완료 기준:
- 저장소에 자산 디렉터리 구조가 생성돼 있다.
- 어떤 Task가 어떤 자산 파일로 이동하는지 매핑이 정리돼 있다.

### 2. Python 스크립트 원본 분리

목표:
- 현재 코드 내부에 있는 Python 스크립트 본문을 평문 파일로 옮긴다.

작업:
- `prepare_build.py`, `run_build.py`, `run_coverity.py`, `run_custom_analysis.py`, `trigger_follow_up.py` 원본 자산 생성
- 스크립트 내부에서 필요한 플레이스홀더 식별
- 현재 생성 결과와 의미가 달라지지 않도록 원본 보존

완료 기준:
- 공통 Python 스크립트가 저장소 파일로 존재한다.
- 코드 내부에 스크립트 본문 대형 문자열이 직접 남아 있지 않거나, 최소한 점진 제거 대상이 명확하다.

### 3. 자산 로더 도입

목표:
- 생성기가 자산 파일을 읽어 올 수 있게 한다.

작업:
- `src/bamboo_spec_generator/script_assets.py` 추가
- Task명과 언어 기준으로 기본 자산 파일을 찾는 함수 구현
- 파일 누락 시 명확한 오류를 반환하는 처리 추가

완료 기준:
- 생성기가 스크립트 자산 파일을 읽어 문자열로 가져올 수 있다.
- 자산 누락 오류가 테스트 가능한 형태로 노출된다.

### 4. 렌더러 도입

목표:
- 공통 자산에 빌드 정의 값을 주입해 최종 스크립트를 만든다.

작업:
- `src/bamboo_spec_generator/script_renderer.py` 추가
- `ScriptRenderContext` 개념 반영
- 플레이스홀더 치환 구현
- 줄바꿈, 공백 등 최소 정규화 구현
- 미치환 플레이스홀더 검증 추가

완료 기준:
- 빌드 정의 입력으로 Task별 최종 스크립트 문자열을 렌더링할 수 있다.
- 렌더링 실패와 미치환 변수 오류가 구분된다.

### 5. 생성기 연동

목표:
- `generator.py`가 직접 스크립트 내용을 만들지 않고 렌더러를 사용하도록 바꾼다.

작업:
- 기존 스크립트 생성 함수 호출부를 자산 로더/렌더러 기반으로 교체
- Java inline body 출력은 유지
- 기존 생성 클래스명, stage 구조, task 구조는 변경하지 않음

완료 기준:
- 동일 입력에 대해 기존과 의미상 동일한 Java 생성 결과가 나온다.
- 스크립트 본문은 자산 파일을 기준으로 생성된다.

### 6. 오버레이 구조 도입

목표:
- OS/컴파일러별 차이를 공통 자산에서 분리한다.

작업:
- `windows`, `linux`, `compiler/vs2022` 등 필요한 오버레이 규칙 도입
- MSBuild/Visual Studio 환경 설정처럼 공통 자산에서 분리해야 할 내용을 오버레이로 이동
- `subPath` 반영 같은 경로 차이를 렌더링 컨텍스트로 연결

완료 기준:
- 공통 자산 안의 과도한 환경 분기가 줄어든다.
- Windows/Linux 또는 compiler별 차이가 별도 구조로 드러난다.

### 7. 언어별 스크립트 확장

목표:
- `py` 외에 `bat`, `sh` 자산 구조를 실제 Task에 적용한다.

작업:
- OS별 진입 스크립트 필요 여부 검토
- `bat`, `sh` 자산 추가
- Python 보조 스크립트와 OS별 래퍼 스크립트 결합 전략 구현

완료 기준:
- 적어도 하나 이상의 Task에서 `bat` 또는 `sh` 파일 자산이 실제로 사용된다.
- 언어별 파일 구조가 문서뿐 아니라 구현에도 반영된다.

### 8. 검증 및 테스트 보강

목표:
- 새 구조가 회귀 없이 유지되도록 테스트를 확장한다.

작업:
- 자산 파일 존재 검증 테스트 추가
- 렌더링 단위 테스트 추가
- 통합 생성 테스트에서 자산 기반 스크립트 반영 여부 검증
- 필요 시 스냅샷 성격의 비교 테스트 도입

완료 기준:
- 자산 선택, 렌더링, 통합 생성이 테스트로 커버된다.
- 스크립트 자산 변경 시 회귀를 빠르게 감지할 수 있다.

### 9. 문서 및 운영 가이드 갱신

목표:
- 실제 저장소 구조와 운영 방식을 문서에 반영한다.

작업:
- `README.md`에 스크립트 자산 위치와 수정 방법 추가
- 새 자산 디렉터리와 생성 흐름 설명 반영
- 향후 contributor가 따라야 할 규칙 문서화

완료 기준:
- 문서와 실제 저장소 상태가 일치한다.
- 공통 스크립트 수정 후 생성 결과 반영 절차가 README에 정리돼 있다.

## 권장 구현 순서

1. 자산 구조 스캐폴딩
2. Python 스크립트 원본 분리
3. 자산 로더 도입
4. 렌더러 도입
5. 생성기 연동
6. 테스트 보강
7. 오버레이 구조 도입
8. `bat`/`sh` 확장
9. README 정리

## 최소 구현 범위

첫 구현은 다음까지를 MVP로 본다.

- `scripts/plan_tasks/common/py/` 도입
- Python 스크립트 자산 분리
- 자산 로더/렌더러 추가
- `generator.py` 연동
- 기존 테스트 갱신 및 추가

이 범위만 완료해도 "스크립트 원본이 코드 내부 문자열이 아니라 저장소 파일로 관리된다"는 요구사항의 핵심을 충족할 수 있다.

## 리스크와 대응

- 생성 결과 차이 발생
  - 대응: 기존 테스트와 새 통합 테스트를 함께 유지한다.
- 플레이스홀더 누락
  - 대응: 렌더링 단계에서 미치환 토큰을 오류로 처리한다.
- 공통 자산에 환경 분기 재집중
  - 대응: 오버레이 도입을 후순위가 아니라 명시된 단계로 유지한다.
- Windows/Linux 차이 확장 지연
  - 대응: 1차는 Python 자산 분리, 2차에서 `bat`/`sh`를 확장한다.

## 오픈 이슈

- `run_custom_analysis`를 독립 자산으로 둘지 command list 조립 템플릿으로 둘지 결정 필요
- 자산 디렉터리를 저장소 루트 `scripts/`에 둘지 `src` 하위 리소스로 둘지 최종 확정 필요
- 장기적으로 생성 산출물 안에 스크립트 파일을 함께 기록할지 여부 검토 필요
