# CRS: bamboo_spec_generator 통합 요구사항

## 문서 메타데이터

- 문서 일자: 2026-03-24
- 문서 유형: CRS
- 상태: 초안
- 대상 프로젝트: `bamboo_spec_generator`
- Jira 전환 대상: Requirement / Epic / Story 초안

## 요약

`bamboo_spec_generator`는 연도별 JSON 또는 향후 DB에 저장된 빌드 정의를 기준으로 Bamboo Specs Java 코드를 생성하는 로컬 실행형 생성기에서 출발했지만, 장기적으로는 Bamboo 기반 CI/CD 전반을 관리하는 운영 시스템으로 발전해야 한다. 시스템은 다중 빌드 플랜 생성뿐 아니라 공통 워크플로우, Bitbucket 저장소 연결, 브랜치 트리거, 스크립트 자산 관리, 빌드 작업 하위 경로, MSBuild 보정, 빌드 메타데이터 및 실행 이력의 DB 관리, 배포 파이프라인과 릴리스 흐름 관리, 환경별 배포 상태 추적, 운영 백엔드/API/조회 UI, 프로젝트 등록/관리, 사용자 관리, 빌드 현황 조회, Bamboo 시스템 운영 현황 조회를 함께 지원해야 한다.

## 현재 상태

- 현재 구현 기준 입력 소스는 연도별 JSON 파일이다.
- 현재 구현은 단일 Bamboo Specs 프로젝트 생성, 공통 워크플로우, 작업 하위 경로, MSBuild 보정용 스크립트 자산, Python 기반 Task 스크립트 렌더링을 지원한다.
- 생성기는 운영 백엔드 API에서 활성 빌드 정의를 읽기 위한 클라이언트와 `--api-plan-key` 진입점을 가진다.
- Django 기반 운영 백엔드에는 ORM 모델, migration, Admin, Ninja API, 프로젝트 등록/수정, 조회용 웹 UI, BuildInfo 관리 화면이 추가되었다.
- 운영 백엔드는 개발 기본값으로 SQLite를 사용하고, 환경변수 스위치로 PostgreSQL로 전환할 수 있다.
- 개발용 DB 초기화 명령 `init_dev_db`, PostgreSQL 초기화 명령 `init_postgres_db --force`가 추가되었다.
- JSON 빌드 정의 import/sync 관리 명령과 정의 변경 이력 관리가 추가되었다.
- 빌드 결과 저장, 버전 관리, 동일 커밋 재빌드 처리 규칙은 백엔드 서비스 계층에 초안 수준으로 반영되었지만 실제 Bamboo 연동과 end-to-end 적재는 아직 미완료다.
- Bitbucket 저장소 식별 정보, 브랜치 트리거, `create_if_missing` 기반 plan-local repository 생성은 Java Specs 생성에 반영되어 있다.
- 운영 설정으로 Git clone URL 템플릿, 기본 repository linkage mode, Bamboo 서버 URL, Coverity 설정을 DB에서 관리할 수 있다.
- 등록된 프로젝트 메타데이터와 `BuildPlanBuildInfo`를 조합해 활성 정의/준비 컨텍스트를 합성하고 Specs preview/export draft를 생성할 수 있다.
- 운영 UI와 서비스에는 Bamboo plan 상태/상세 조회, Specs publish, Bamboo 실행 요청, publish 이력 저장이 부분 구현되어 있다.

## 배경

- Bamboo 플랜을 수작업으로 반복 구성하면 설정 편차와 유지보수 비용이 커진다.
- JSON 기반 빌드 정의는 초기 선언형 입력 모델로 적합하다.
- 실제 운영에서는 저장소 연결, 브랜치 트리거, 공통 스크립트 관리, MSBuild 예외 처리, 하위 작업 경로 같은 운영 규칙이 함께 필요하다.
- 시간이 지나면 빌드 결과, 버전 정보, 실패 위치, 정적분석 결과 같은 운영 메타데이터도 함께 관리해야 하므로 DB 중심 구조가 필요하다.
- 운영 메타데이터를 사람과 시스템이 함께 사용할 수 있으려면 관리용 백엔드, 조회 API, 조회 화면도 필요하다.
- 빌드 생성만으로는 운영 목적을 충분히 달성하기 어렵고, 실제 서비스 운영에서는 배포 대상 환경, 릴리스 승인, 배포 결과, 롤백 가능성, 변경 이력까지 함께 관리해야 한다.
- 운영 관점에서는 프로젝트 등록, 프로젝트 정보 수정, 사용자 관리, 빌드 현황 모니터링, Bamboo 에이전트와 수행 중 작업 확인 같은 콘솔 기능이 함께 필요하다.
- 운영 기능은 UI와 별개로 API를 통해 외부 시스템이나 내부 자동화에서도 재사용 가능해야 한다.
- 프로젝트 등록 정보가 충분하면 이를 생성기 입력으로 변환해 Bamboo Specs 빌드 플랜 생성과 등록 흐름까지 연결할 수 있어야 한다.
- 운영자가 프로젝트를 쉽게 온보딩할 수 있으려면 메인 페이지에서 즉시 접근 가능한 등록 UI, 기존 등록값 재사용, 저장소 하위의 빌드 입력 구조가 필요하다.

## 문제

현재와 같은 날짜별 개별 문서와 파일 중심 입력 구조만으로는 전체 제품 요구사항을 한 번에 파악하기 어렵고, 빌드 정의와 운영 결과를 통합적으로 추적하기도 어렵다. 또한 스크립트 자산, 저장소 연결, 버전 규칙, 동일 커밋 재빌드 같은 규칙이 분산되면 구현과 운영 판단이 일관되지 않게 된다.

## 범위

### 포함 범위

- 연도별 JSON 빌드 정의 관리와 Bamboo Specs Java 코드 생성
- 단일 Specs 저장소 내 다중 플랜 생성
- Bamboo 빌드 플랜, 배포 프로젝트, 릴리스/배포 파이프라인의 통합 관리 방향 정의
- Bitbucket 저장소 연결 및 `dev`, `release`, `master` 브랜치 트리거 구성
- 공통 워크플로우 템플릿과 빌드 상세 설정 분리
- 빌드 작업 하위 경로 지정
- MSBuild 플랜용 `Directory.Build.targets` 사전 생성과 Visual Studio 환경 설정 로드
- 플랜 스크립트 자산의 파일 기반 관리와 환경별 커스터마이징
- 빌드 정의, 빌드 결과, 버전, 정적분석 결과, 실패 위치, 변경 이력의 DB 관리
- 배포 대상 환경, 배포 이력, 릴리스 버전, 승인 상태, 롤백 가능 버전의 관리
- 빌드 준비 스테이지 시작 시 DB 메타데이터를 읽어 변수 형태로 사용할 수 있는 구조
- 프로젝트 단위 메타데이터와 다중 저장소/다중 빌드 관계 관리
- PostgreSQL 기반 운영 데이터 저장소
- Django 기반 운영 백엔드
- Ninja 기반 조회/적재 API
- 조회용 웹 프론트엔드
- 프로젝트 등록, 조회, 수정 관리 기능
- 사용자 및 권한 관리 기능
- 빌드 현황 조회와 Bamboo 시스템 운영 현황 조회 기능
- 운영 기능 전반의 API 우선 제공
- 등록된 프로젝트를 기반으로 한 Specs 생성기 연동 및 빌드 플랜 등록 흐름

### 제외 범위

- Bamboo 서버 자동 배포
- GUI 기반 입력 편집기
- Bamboo 외 다른 CI/CD 도구 지원
- Bitbucket 저장소 생성 및 권한 자동화
- 빌드 정의 편집 전용 고급 관리 UI

## 요구사항

### 기능 요구사항

- 시스템은 하나 이상의 JSON 빌드 정의를 읽어 Bamboo Specs Java 코드를 생성할 수 있어야 한다.
- 시스템은 연도별 입력 구조를 지원해야 한다.
- 시스템은 여러 빌드 정의를 하나의 Bamboo Specs 프로젝트 안에서 함께 생성할 수 있어야 한다.
- 시스템은 공통 워크플로우를 사용해야 하며, 스테이지 순서는 `빌드 준비 -> 빌드 -> 정적분석 -> 후속 작업 트리거`로 고정해야 한다.
- 시스템은 Bitbucket 저장소를 `projectKey`, `repoSlug` 기준으로 식별할 수 있어야 한다.
- 시스템은 저장소 연결 모드로 최소 `linked`, `create_if_missing`를 지원할 수 있어야 한다.
- 시스템은 `dev`, `release`, `master` 브랜치를 기본 연결 및 트리거 대상으로 다뤄야 한다.
- 시스템은 입력 JSON에서 빌드 작업 하위 경로를 읽고, 준비, 빌드, 정적분석 단계에서 해당 경로를 작업 디렉터리로 사용할 수 있어야 한다.
- 시스템은 MSBuild 기반 플랜을 식별하고, 실제 MSBuild 호출 전 `Directory.Build.targets`를 생성할 수 있어야 한다.
- 시스템은 Visual Studio 환경 설정 스크립트 경로를 기준으로 MSBuild 실행 환경을 로드할 수 있어야 한다.
- 시스템은 플랜 Task 스크립트를 공통 자산과 환경별 차이로 분리해 저장소 파일로 관리할 수 있어야 한다.
- 시스템은 최소한 `py`, `sh`, `bat` 스크립트 자산 관리를 지원 대상으로 고려해야 한다.
- 시스템은 현재 JSON으로 관리하는 빌드 정의를 DB에 저장할 수 있어야 한다.
- 시스템은 빌드 준비 스테이지 시작 시 DB에서 프로젝트 및 저장소 메타데이터를 읽어 변수로 등록할 수 있어야 한다.
- 시스템은 DB에서 최소한 `jira project key`, `bitbucket project key`, `bitbucket repo slug`, `coverity project`, `coverity stream`, `대표 repo slug`를 조회할 수 있어야 한다.
- 시스템은 하나의 프로젝트에 여러 빌드가 연결될 수 있는 구조를 관리할 수 있어야 한다.
- 시스템은 프로젝트 단위로 여러 저장소를 관리할 수 있어야 하며, 결과 취합 시 프로젝트에 등록된 모든 저장소 정보를 함께 확인할 수 있어야 한다.
- 시스템은 각 빌드 플랜의 실행 결과를 DB에 저장할 수 있어야 한다.
- 시스템은 빌드 결과에 최소한 빌드 번호, 버전, 커밋 해시, 성공 여부, 결과 상태, 정적분석 결과, 요약 메시지를 저장할 수 있어야 한다.
- 시스템은 빌드 실패 시 실패한 스테이지와 잡을 저장할 수 있어야 하며, 가능하면 태스크까지 저장할 수 있어야 한다.
- 시스템은 빌드 결과를 배포 가능 산출물과 연결할 수 있어야 한다.
- 시스템은 빌드 플랜 이후의 배포 단계, 환경별 배포 여부, 배포 결과를 저장하고 추적할 수 있어야 한다.
- 시스템은 릴리스 후보, 승인 대기, 배포 완료, 배포 실패, 롤백 완료 같은 상위 CD 상태를 표현할 수 있어야 한다.
- 시스템은 환경별 최근 배포 버전과 직전 안정 버전을 조회할 수 있어야 한다.
- 시스템은 빌드 버전을 `vX.X.X` 형식으로 관리할 수 있어야 한다.
- 시스템은 `master` 빌드 시 major를 증가시키고 하위 번호를 `0`으로 초기화할 수 있어야 한다.
- 시스템은 `release` 빌드 시 minor를 증가시키고 patch를 `0`으로 초기화할 수 있어야 한다.
- 시스템은 `dev` 빌드 시 patch를 증가시킬 수 있어야 한다.
- 시스템은 빌드 플랜별 최신 버전 정보를 별도로 보유하거나 즉시 조회할 수 있어야 한다.
- 시스템은 동일 커밋 재빌드 시 기존 버전 레코드를 조회하고 해당 버전에 최신 결과를 갱신할 수 있어야 한다.
- 시스템은 생성기가 운영 백엔드의 Ninja API를 통해 활성 빌드 정의를 조회해 Specs 생성에 사용할 수 있어야 한다.
- 시스템은 생성기 또는 생성된 준비 스크립트가 DB 조회 결과를 빌드 준비 단계 변수로 전달할 수 있어야 한다.
- 시스템은 PostgreSQL을 운영 DBMS로 사용할 수 있어야 한다.
- 시스템은 Django 기반 백엔드에서 빌드 정의, 프로젝트/저장소 메타데이터, 실행 결과, 버전 정보를 관리할 수 있어야 한다.
- 시스템은 Django 기반 백엔드에서 배포 환경, 릴리스, 배포 이력, 승인 상태를 관리할 수 있어야 한다.
- 시스템은 Ninja 기반 API로 빌드 정의 조회, 프로젝트 조회, 빌드 결과 조회, 빌드 결과 적재, 배포 상태 조회, 배포 결과 적재를 지원할 수 있어야 한다.
- 시스템은 조회용 웹 프론트엔드에서 프로젝트, 저장소, 플랜, 버전, 실행 이력, 정적분석 결과뿐 아니라 배포 상태와 릴리스 흐름을 탐색할 수 있어야 한다.
- 시스템은 운영자가 신규 프로젝트를 등록하고 프로젝트-저장소-플랜 연계를 관리할 수 있어야 한다.
- 시스템은 프로젝트 등록 UI를 기본적으로 접힌 상태로 제공하고, 사용자가 명시적으로 등록 버튼을 눌렀을 때만 펼칠 수 있어야 한다.
- 시스템은 프로젝트 등록 시 기존에 등록된 Jira Project Key, Bitbucket Project Key, 저장소 정보, Coverity 정보를 선택 후보로 재사용할 수 있어야 한다.
- 시스템은 하나의 프로젝트에 여러 저장소를 등록할 수 있어야 하며, 빌드 항목은 저장소 하위 항목으로 입력되고 관리될 수 있어야 한다.
- 시스템은 빌드 등록 시 최소한 `빌드 이름`, `빌드 플랜 키`, `언어`, `컴파일러`를 입력할 수 있어야 한다.
- 시스템은 `언어`와 `컴파일러`에 대해 현재 시스템이 지원하는 목록을 선택형으로 제공할 수 있어야 한다.
- 시스템은 등록된 프로젝트 정보가 충분하면 이를 기준으로 Bamboo Specs 생성 입력을 구성할 수 있어야 한다.
- 시스템은 등록된 프로젝트를 기준으로 빌드 플랜 생성과 등록 흐름을 시작할 수 있어야 한다.
- 시스템은 운영자가 프로젝트 기본 정보와 운영 메타데이터를 조회하고 수정할 수 있어야 한다.
- 시스템은 사용자 계정, 역할, 접근 범위를 관리할 수 있어야 한다.
- 시스템은 빌드 현황을 프로젝트별, 플랜별, 상태별로 조회할 수 있어야 한다.
- 시스템은 Bamboo 시스템 관점에서 에이전트 상태, 실행 중인 작업, 대기 중인 작업 같은 운영 현황을 조회할 수 있어야 한다.
- 시스템은 프로젝트 관리, 사용자 관리, 빌드 현황 조회, Bamboo 시스템 운영 현황 조회 기능을 모두 HTTP API로 제공할 수 있어야 한다.

### 비기능 요구사항

- 동일 입력에 대해 생성 결과는 반복 실행 시 일관되어야 한다.
- 입력 포맷과 스크립트 자산 구조는 사람이 읽고 검토하기 쉬워야 한다.
- 공통 워크플로우와 자산 구조는 플랜 간 편차를 최소화해야 한다.
- 하위 경로, 스크립트 자산, MSBuild 보정, DB 전환은 기존 흐름을 즉시 깨지 않고 단계적으로 적용 가능해야 한다.
- 버전 및 결과 이력은 감사 추적과 운영 판단에 활용 가능해야 한다.
- 프로젝트/저장소/빌드 메타데이터는 다중 저장소, 다중 빌드 구조를 추적 가능하게 유지해야 한다.
- 비밀값, 토큰, 인증 정보는 입력 JSON이나 문서에 포함되지 않아야 한다.
- 운영 백엔드와 API는 생성기 본체와 책임이 분리되어야 한다.
- 빌드 관리와 배포 관리 데이터는 동일 운영 콘솔에서 이어서 탐색 가능해야 한다.
- 배포/승인 관련 변경 이력은 감사 추적 가능해야 한다.
- 운영 관리 기능의 API는 UI 없이도 자동화 연동이 가능하도록 일관된 리소스 구조와 인증 경계를 가져야 한다.
- 프로젝트 등록 데이터와 생성기 입력 모델 간 매핑은 추적 가능해야 하며, 생성 실패 시 원인을 식별 가능해야 한다.

## 입력 및 출력

### 입력

- `build_info_json/<year>/<buildId>.json` 형태의 빌드 정의 파일
- 저장소 정보, 에이전트 요구사항, 빌드 명령, 정적분석 명령, 후속 트리거 설정
- 선택적 빌드 작업 하위 경로
- 향후 DB에 저장된 활성 빌드 정의와 빌드 메타데이터

### 출력

- Bamboo Specs Java 소스 코드와 관련 산출물
- 스크립트 번들, Coverity 설정, 보조 스크립트 자산
- 빌드 플랜별 버전 및 실행 결과 메타데이터

## 수용 기준

- JSON 기반 입력, 단일 Specs 저장소 생성, 저장소 연결, 브랜치 트리거 요구가 함께 정의되어 있다.
- 작업 하위 경로, MSBuild 보정, 스크립트 자산 분리 요구가 포함되어 있다.
- DB 기반 빌드 정의/결과/버전 관리 요구가 포함되어 있다.
- 빌드 준비 스테이지에서 사용할 프로젝트/저장소 메타데이터 DB 조회 요구가 포함되어 있다.
- 실패 위치 저장, 버전 규칙, 동일 커밋 재빌드 규칙이 포함되어 있다.
- Django 기반 운영 백엔드, Ninja API, 조회용 프론트엔드 요구가 포함되어 있다.
- 프로젝트 등록/수정, 사용자 관리, 빌드 현황 조회, Bamboo 시스템 운영 현황 조회 요구가 포함되어 있다.
- 신규 운영 기능이 API 우선 원칙으로 정의되어 있다.
- 프로젝트 등록 UI의 접힘/펼침, 기존 등록값 재사용, 저장소 하위 빌드 입력, 지원 언어/컴파일러 선택 요구가 포함되어 있다.
- 등록 프로젝트 기반의 Specs 생성기 연동과 빌드 플랜 등록 요구가 포함되어 있다.

## 제약/가정

- 연도 정보는 기본적으로 디렉터리 구조에서 해석한다.
- 초기 입력 소스는 JSON이지만 장기적으로 DB가 시스템 오브 레코드가 되는 방향을 가정한다.
- 현재 구현은 JSON 입력이 기본이며, 운영 API 기반 입력은 단일 `plan_key` 조회 경로로 부분 구현되었다.
- 운영 DB를 생성기가 직접 조회하는 경로는 없으며, DB 기반 요구사항은 Django/Ninja API를 통한 접근을 전제로 한다.
- `release`는 초기 범위에서 단일 브랜치명으로 본다.
- MSBuild 관련 상세 예외는 후속 설계에서 구체화한다.
- 운영 DBMS는 PostgreSQL을 사용한다.
- 개발 편의상 로컬 기본 백엔드 DB는 SQLite를 허용한다.
- Bamboo 시스템 운영 현황 조회는 Bamboo가 제공하는 API 또는 동등한 연계 수단이 존재함을 가정한다.
- 프로젝트 등록 정보만으로 생성이 가능하려면 생성기에 필요한 필수 메타데이터 세트가 별도로 정의되어야 한다.

## 오픈 이슈

- 비등록 저장소를 어떤 Bamboo 모델로 표현할지 추가 검토가 필요하다.
- `master`, `release`, `dev` 이외 브랜치의 버전 규칙을 허용할지 결정이 필요하다.
- 실패 위치를 모든 빌드 타입에서 태스크 단위까지 확보할 수 있는지 확인이 필요하다.
- 생성기는 보안상 DB 직접 조회 대신 Django/Ninja API를 경유해야 한다.
- 사용자 관리 범위를 로컬 계정 관리로 시작할지 SSO/사내 인증 연동까지 포함할지 결정이 필요하다.
- Bamboo 운영 현황 조회를 읽기 전용으로 둘지 제어 기능까지 확장할지 결정이 필요하다.
- 프로젝트 등록 후 플랜 생성만 지원할지, Bamboo 반영 또는 등록까지 지원할지 운영 단계별 범위 확정이 필요하다.
- 지원 언어와 컴파일러 목록을 정적 설정으로 둘지 운영 데이터로 관리할지 결정이 필요하다.
