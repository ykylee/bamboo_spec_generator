## 요약

빌드 구성은 `stage -> job -> task` 계층의 모듈 조합으로 정의할 수 있어야 하며, `task`는 공통 표준화 대신 Bamboo, Jenkins 같은 CI 도구별 스키마로 세분화할 수 있어야 한다. 또한 정해진 형식의 모듈 정의 파일을 정해진 위치에 두면 자동 로딩되어야 하며, 운영 웹에서 선언형 모듈과 스크립트 자산 업로드를 수행할 수 있는 방향도 함께 검토해야 한다.

## 배경

- 현재 생성기는 Bamboo 중심의 고정된 워크플로우와 스크립트 자산 렌더링 구조를 가진다.
- 향후 Jenkins까지 수용하려면 `task` 개념을 억지로 공통화하기보다 도구별 차이를 구조적으로 허용하는 편이 안전하다.
- 실제 운영에서는 공통 단계 틀은 유지하되, 팀/시스템별로 stage, job, task 조합을 유연하게 바꾸고 싶어하는 요구가 있다.
- Python 기반 스크립트는 동일한 본문을 유지하면서 OS별 실행 헤더와 런처만 달라져야 하는 경우가 많다.
- 확장 모듈 등록을 코드 변경 없이 운영 레벨에서 반영하려면 파일 배치와 자동 로딩 규칙이 필요하다.

## 설명

시스템은 빌드 구성을 선언형 모듈 조합으로 표현할 수 있어야 한다. 최상위 `stage`는 순서를 가진 실행 묶음이고, 각 `stage`는 하나 이상의 `job` 모듈로 구성되며, 각 `job`은 순차 실행되는 `task` 목록을 가진다. 다만 `task`는 Bamboo와 Jenkins의 실행 단위가 서로 다르므로 공통 enum으로 강제하지 않고, `ci_provider`별 전용 모델과 검증 규칙을 사용해야 한다.

각 모듈의 선언 모델과 실제 렌더링/실행 구현은 분리되어야 한다. 코어는 조합 규칙, 의존성, 검증, 렌더러 진입점만 제공하고, 실제 task provider, 스크립트 템플릿, task renderer는 내부 기본 구현 또는 외부 확장 패키지로 등록할 수 있어야 한다. `stage`, `job`, `task` 모듈은 정해진 스키마의 파일로 정의되며, 시스템은 정해진 디렉터리를 스캔해 유효한 모듈을 자동 로딩해야 한다.

운영 웹 업로드는 검토 가치가 있다. 다만 임의 Python 코드나 renderer 구현 전체를 웹에서 직접 업로드하는 방식은 보안과 운영 통제가 어렵다. 따라서 1차 범위에서는 선언형 모듈 정의 파일과 스크립트 템플릿 자산 업로드를 우선 검토하고, 코드 실행이 필요한 provider 확장은 저장소 반영 또는 관리 배포 절차를 유지하는 방향이 적절하다.

`script` 계열 Task는 인라인 문자열보다 파일 기반 템플릿을 기본값으로 둔다. `shell`, `powershell`, `bat` 같은 OS 종속 스크립트는 각 OS 전용 자산으로 직접 관리할 수 있다. 반면 `python` task는 입력 모델을 OS 비종속 Python 코드로 유지하고, 렌더링 시점에 대상 OS에 맞는 실행 헤더와 런처 정책을 적용해야 한다. 예를 들어 Linux에서는 `#!/usr/bin/env python3` shebang과 실행 권한을 적용하고, Windows에서는 `#!python` 또는 wrapper를 통해 실행하도록 생성할 수 있어야 한다.

## 범위

### 포함

- `stage -> job -> task` 계층의 모듈형 빌드 구성 모델
- stage/job 조합 규칙과 순서/의존성 표현
- CI 도구별 task 스키마 분리
- Bamboo 전용 task와 Jenkins 전용 task의 독립 검증 규칙
- task/provider/renderer/템플릿의 등록형 확장 구조
- 정해진 위치의 모듈 정의 파일 자동 로딩
- 파일 기반 스크립트 템플릿 자산 관리
- Python task의 OS별 헤더/런처 변환 정책
- 외부 시스템이 코어 수정 없이 모듈을 추가할 수 있는 인터페이스 정의
- 선언형 모듈과 스크립트 자산의 웹 업로드 검토

### 제외

- Jenkins step 전체를 초기 1차 범위에서 완전 열거하는 작업
- Bamboo/Jenkins 서버에 대한 실제 원격 생성 자동화
- Python 본문 로직의 OS별 의미 변환 자동화

## 수용 기준

- 시스템이 빌드 구성을 `stage`, `job`, `task` 모듈 계층으로 정의한다고 명시된다.
- `stage`와 `job`이 독립 모듈로 선언되고 조합 가능하다고 정의된다.
- `task`는 공통 단일 표준 대신 CI 도구별 전용 스키마로 관리한다고 정의된다.
- Bamboo용 task와 Jenkins용 task가 서로 다른 검증 규칙과 렌더링 경로를 가질 수 있다고 정의된다.
- 모듈 선언 모델과 실제 구현 코드가 분리된다고 정의된다.
- 외부 시스템이 provider 또는 renderer를 추가 등록할 수 있는 확장 지점이 정의된다.
- 정해진 형식의 stage/job/task 파일을 정해진 경로에 두면 자동 로딩할 수 있다고 정의된다.
- `script` 계열 task가 파일 기반 템플릿을 기본으로 사용한다고 정의된다.
- `python task`가 OS 비종속 소스 모델을 입력으로 받고, 대상 OS에 따라 shebang, wrapper, 실행 명령을 바꿔 렌더링할 수 있다고 정의된다.
- Linux용 Python 실행 헤더로 `#!/usr/bin/env python3`를 사용할 수 있는 정책이 포함된다.
- Windows용 Python 실행 방식으로 `#!python` 또는 wrapper 기반 실행 정책이 포함된다.
- 웹 업로드는 선언형 모듈 정의와 스크립트 자산 범위를 우선 검토하고, 임의 코드 업로드는 별도 통제 대상으로 본다고 정의된다.
