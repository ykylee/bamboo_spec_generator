# EPIC-02 빌드 메타데이터 및 실행 이력의 DB 관리 전환

## 유형

- Epic

## 구현 상태

- 부분 구현
- Django 백엔드 스캐폴딩, ORM 모델, migration, 기본 API/UI, 생성기 API 클라이언트가 추가되었다.
- 실제 JSON 적재, Bamboo 준비 스테이지 연동, 운영 데이터의 end-to-end 적재는 아직 미완료다.

## 우선순위

- 차기 핵심 확장 Epic

## 요약

현재 JSON 파일로 관리하는 빌드 정의를 DB 기반 관리 체계로 전환하고, 여기에 빌드 플랜별 실행 결과와 버전 정보를 함께 저장해 생성과 운영 추적의 기준 데이터로 활용할 수 있어야 한다. 또한 PostgreSQL 기반 운영 데이터 저장소 위에 Django 기반 백엔드, Ninja API, 조회용 프론트엔드를 제공해 운영 메타데이터를 사람과 시스템이 함께 활용할 수 있어야 한다.

## 배경

- 현재 생성기는 연도별 JSON 파일을 읽어 Bamboo Specs를 생성한다.
- 운영 단계에서는 빌드 결과, 빌드 번호, 커밋 해시, 정적 분석 결과, 버전 식별자 같은 누적 데이터를 함께 관리해야 한다.
- JSON 파일만으로는 정의 데이터와 실행 데이터를 일관되게 연결하기 어렵고 조회와 감사 추적도 제한적이다.
- 운영 메타데이터가 늘어나면 단순 DB 적재만으로는 부족하고, 조회 API와 운영 화면이 필요하다.

## 설명

시스템은 기존 JSON 기반 빌드 정의를 DB에서 관리할 수 있어야 하며, 생성기는 점진적으로 이 DB를 기준 데이터 소스로 사용할 수 있어야 한다. 또한 각 빌드 플랜의 실행 결과와 버전 정보를 정의 데이터와 연결해 저장해야 한다. 빌드 플랜은 현재 기준의 최신 버전 정보를 별도로 가져야 하며, 동일 커밋에 대한 재빌드가 시작되면 기존 버전 레코드를 확인해 해당 버전에 최신 결과를 업데이트할 수 있어야 한다. 이를 통해 특정 빌드 정의가 어떤 버전으로 언제 실행되었고 어떤 결과를 냈는지 추적 가능해야 하며, 변경 이력과 활성 정의 상태를 기준으로 안정적으로 Bamboo Specs를 생성할 수 있어야 한다. 운영 계층은 Django 기반으로 분리하고, API는 Ninja를 사용하며, 초기 웹 UI는 조회 중심으로 제공한다.

- 생성기가 DB를 기준 데이터 소스로 사용할 전환 전략이 정의된다.
- JSON 기반 초기 데이터 이전 또는 병행 운영 전략이 포함된다.

- 생성기는 보안상 운영 백엔드의 DB를 직접 읽지 않고 Ninja API를 경유해야 한다.
