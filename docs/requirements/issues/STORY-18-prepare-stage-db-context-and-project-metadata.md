- 다중 저장소/다중 빌드 프로젝트의 취합 조회 규칙 정의

## 요약

빌드 준비 스테이지가 시작될 때 DB에서 프로젝트 및 저장소 메타데이터를 읽어 변수로 등록하고, 프로젝트 단위의 다중 저장소/다중 빌드 구조를 함께 표현할 수 있어야 한다.

## 배경

운영 프로젝트는 하나의 저장소와 하나의 빌드만 갖지 않을 수 있다. 예를 들어 하나의 프로젝트 아래에 `frontend Node.js`, `backend python` 같은 여러 빌드가 있을 수 있고, 여러 저장소를 묶어 하나의 프로젝트로 관리할 수도 있다. 이 경우 빌드 준비 단계에서 공통 프로젝트 메타데이터를 읽어 변수 형태로 제공하면 후속 스크립트와 결과 정리에 활용하기 쉽다.

## 설명

시스템은 빌드 준비 스테이지 시작 시 DB에서 현재 빌드가 속한 프로젝트의 메타데이터를 조회할 수 있어야 한다. 조회 대상에는 최소한 `jira project key`, `bitbucket project key`, `bitbucket repo slug`, `coverity project`, `coverity stream`, `대표 repo slug`가 포함되어야 한다. 또한 프로젝트마다 여러 빌드가 있을 수 있고, 여러 저장소를 가질 수 있어야 하므로 프로젝트-저장소-빌드 관계를 함께 모델링해야 한다. 결과 취합 시에는 현재 플랜에만 연결된 저장소가 아니라 프로젝트에 등록된 전체 저장소 정보를 확인할 수 있어야 한다.

## 수용 기준

- 준비 스테이지 시작 시 DB에서 프로젝트 메타데이터를 조회해야 한다는 요구사항이 정의되어 있다.
- 최소 조회 대상에 `jira project key`, `bitbucket project key`, `bitbucket repo slug`, `coverity project`, `coverity stream`, `대표 repo slug`가 포함되어 있다.
- 조회한 값을 준비 스테이지에서 사용할 변수로 등록할 수 있다고 정의되어 있다.
- 하나의 프로젝트가 여러 빌드와 여러 저장소를 가질 수 있는 구조가 정의되어 있다.
- 프로젝트 결과 취합 시 프로젝트에 등록된 모든 저장소 정보를 확인할 수 있어야 한다고 정의되어 있다.
