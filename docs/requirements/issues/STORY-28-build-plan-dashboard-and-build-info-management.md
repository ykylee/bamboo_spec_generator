## 요약

운영 콘솔은 프로젝트/저장소/빌드 플랜을 일관된 대시보드 경험으로 제공해야 하며, 빌드 플랜은 플랜 공통 메타데이터와 플랜 하위의 여러 `빌드 정보`를 구분해 관리할 수 있어야 한다. 또한 빌드 플랜 상세에서는 등록된 정보를 바탕으로 실제로 구성될 Bamboo 플랜/잡 구성을 UI에서 확인하고 수정 가능하게 해야 한다.

## 배경

- 최근 운영 UI는 프로젝트 등록/조회에서 시작해 프로젝트 상세, 저장소 상세, 빌드 상세, 빌드 플랜 인덱스로 확장됐다.
- 초기 구현에서는 `빌드 정보`를 실행 이력처럼 다뤘지만, 실제 운영 요구는 Bamboo 플랜 아래 여러 종류의 빌드 환경구성을 별도로 관리하는 것이다.
- 하나의 Bamboo 플랜 안에서도 빌드가 여러 번, 여러 종류로 수행될 수 있으므로 플랜 공통 메타데이터와 개별 빌드 환경구성을 분리해야 한다.
- 추가 확인 결과, `BuildPlan` 1개가 Bamboo `Plan` 1개에 대응하고, 플랜에 연결된 각 `빌드 정보`는 운영 관점에서 `Build Job`과 `Analysis Job`으로 분리된 실행 단위를 가져야 한다.

## 설명

운영 콘솔 UI는 메인 대시보드와 상세 화면 사이의 시각적/동선적 괴리감이 없어야 한다. 상단 네비게이션 검색, 프로젝트 등록/수정 패널, 프로젝트/저장소/빌드 상세, 빌드 플랜 인덱스는 동일한 보드형 대시보드 언어를 사용해야 하며, 자동 스크롤이나 접힘/펼침 동작도 sticky 네비게이션 높이를 고려해 자연스럽게 동작해야 한다.

빌드 플랜은 공통 메타데이터와 개별 `빌드 정보`를 분리해서 관리한다. 플랜 공통 메타데이터는 `정적분석 도구 버전`, `Coverity Project`를 가진다. `빌드 정보`는 플랜 아래 여러 건 존재할 수 있으며, 각 항목은 하나의 소프트웨어 빌드 단위를 대표한다. 이 항목은 `빌드키`, `OS`, `pre process`, `빌드 명령어`, `클린 명령어`, `언어`, `컴파일러`, `분석 제외 파일`, `Coverity Stream`, `빌드 sub path`를 포함해야 한다. 빌드가 실행되는 OS는 플랜 공통이 아니라 각 빌드 정보별로 관리되고, Bamboo Job의 requirements로 분류되어야 한다.

각 `빌드 정보`는 Bamboo 상에서 최소 두 종류의 Job으로 해석되어야 한다. 첫째는 실행 가능한 binary 패키지를 만드는 `Build Job`이고, 둘째는 정적 분석 도구를 수행해 report를 만드는 `Analysis Job`이다. `Analysis Job`은 `Build Job`의 workspace나 산출물을 이어받지 않고, checkout부터 별도로 다시 시작해야 한다. 이렇게 해야 build 실패와 analysis 도구/인프라 실패를 운영상 분리해서 볼 수 있다.

플랜 수준 stage 이름은 다음과 같이 정리한다. `Prepare`는 workspace 준비가 아니라 빌드 시작 시 버전 갱신과 DB 실행 등록을 수행하는 메타데이터 단계다. `Build`는 checkout부터 build와 binary package 생성까지 담당한다. `Analysis`는 checkout부터 다시 시작해 분석 도구 수행과 report 생성을 담당한다. 마지막 `Post Process`는 trigger를 포함한 후속 작업 단계다.

빌드 플랜 상세 화면에서는 등록된 플랜 메타데이터, 활성 정의, 빌드 정보를 결합해 실제로 생성될 Bamboo 플랜 구성을 미리 보여줘야 한다. 사용자는 이 화면에서 Plan 수준 설정과 Job 수준 설정을 확인하고, 수정이 필요한 경우 별도 파일 편집 없이 UI에서 직접 수정할 수 있어야 한다. 이 미리보기는 단순 텍스트 나열이 아니라 Plan/Stage/Job 구조와 각 Job의 핵심 명령어 및 분석 설정이 드러나는 형태여야 한다.

실행 이력은 여전히 별도 데이터로 유지되지만, 앞으로는 실행 시작/종료 시 `buildKey`를 함께 전달해 어떤 `빌드 정보`에 해당하는 실행인지 구분할 수 있어야 한다. 이렇게 하면 같은 플랜 내 여러 빌드의 정적 분석 결과를 빌드키 기준으로 개별 집계하고, 이후 플랜 수준으로 취합할 수 있다.

## 범위

### 포함

- 메인 대시보드와 상세 페이지 간 공통 UI 패턴 정리
- 상단 검색, 접힘/펼침, 스크롤 보정, 부분 페이징 같은 운영 UX 정교화
- 빌드 플랜 인덱스 페이지 추가 및 네비게이션 연결
- 빌드 상세에서 플랜 공통 메타데이터 관리
- 플랜 상세 내에서 플랜 하위 다건 `빌드 정보` 등록/조회/수정
- 빌드 플랜 상세에서 예상 Bamboo Plan/Stage/Job/Task 구성 미리보기
- 예상 Bamboo 구성에서 수정이 필요한 항목을 UI로 직접 수정하는 흐름
- 실행 시작 API에서 `buildKey`를 받을 수 있는 구조 정의
- 빌드키 기준 실행 결과 집계 방향 정의

### 제외

- 실제 Bamboo 잡에서 `buildKey` 전달 로직 구현
- 빌드 정보 삭제/비활성화 정책
- 빌드키별 정적 분석 결과의 최종 집계/리포트 화면
- Bamboo Specs Java/YAML 산출물의 최종 export/publish 화면
- 권한/감사 로그 상세 정책

## 요구사항

- 운영 콘솔 페이지들은 메인 대시보드와 시각 언어가 일관되어야 한다.
- 프로젝트 등록/수정, 저장소 추가, 빌드 추가 패널은 접힘/펼침 상태를 지원해야 한다.
- 자동 스크롤 이동은 sticky 네비게이션 높이를 고려해야 한다.
- 프로젝트 목록 페이징은 전체 페이지 리로드가 아니라 리스트 영역만 갱신할 수 있어야 한다.
- 상단 네비게이션 검색은 빈 입력에서는 결과를 노출하지 않아야 하며, 입력 문자열 포함 기준으로 프로젝트를 필터링해야 한다.
- 빌드 플랜은 `정적분석 도구 버전`, `Coverity Project`를 공통 메타데이터로 관리해야 한다.
- 하나의 빌드 플랜 아래 여러 `빌드 정보`를 등록할 수 있어야 한다.
- 하나의 빌드 플랜은 Bamboo `Plan` 1개를 의미해야 한다.
- 플랜에 연결된 각 `빌드 정보`는 Bamboo 플랜 내부에서 최소 `Build Job` 1개와 `Analysis Job` 1개를 생성하는 기준이 되어야 한다.
- `빌드 정보`는 다음 필드를 가져야 한다.
  - `빌드키`
  - `OS`
  - `pre process`
  - `빌드 명령어`
  - `클린 명령어`
  - `언어`
  - `컴파일러`
  - `분석 제외 파일`
  - `Coverity Stream`
  - `빌드 sub path`
- 실행 시작 API는 선택적으로 `buildKey`를 받을 수 있어야 한다.
- 같은 플랜에서 같은 `buildNumber`라도 서로 다른 `buildKey`면 별도 실행으로 기록할 수 있어야 한다.
- 빌드 플랜 상세 화면은 현재 등록된 정보를 바탕으로 실제 Bamboo 플랜 구성을 미리 보여줄 수 있어야 한다.
- Bamboo 구성 미리보기는 최소한 Plan 식별 정보, Stage/Job 구조, Job별 빌드키, 주요 명령어, 언어/컴파일러, Coverity 관련 설정을 포함해야 한다.
- Bamboo 구성은 `Prepare`, `Build`, `Analysis`, `Post Process` 단계로 표현해야 한다.
- `Prepare` 단계는 새 빌드 시작 등록과 버전 갱신을 담당해야 한다.
- `Analysis Job`은 `Build Job`의 산출물이나 작업 디렉터리를 이어받지 않고 별도 checkout부터 시작해야 한다.
- `Build Job`의 산출물은 배포 가능한 binary package여야 한다.
- `Analysis Job`의 산출물은 각 분석 도구 결과를 정리한 report여야 한다.
- 사용자는 빌드 플랜 상세 화면에서 Bamboo 구성에 영향을 주는 항목을 직접 수정할 수 있어야 하며, 수정 결과는 즉시 미리보기에 반영되어야 한다.

## 수용 기준

- `/build-plans/`에서 빌드 플랜 인덱스를 조회할 수 있다.
- 빌드 상세 화면에서 플랜 공통 메타데이터를 수정할 수 있다.
- 빌드 상세 화면에서 빌드 정보를 등록/조회할 수 있다.
- `/projects/{jira}/builds/{planKey}/infos/{buildKey}/`에서 개별 빌드 정보를 수정할 수 있다.
- 빌드 정보 등록 후 빌드 상세/개별 상세 화면에서 입력한 필드가 조회된다.
- 빌드 상세 화면에서 예상 Bamboo Plan/Stage/Job/Task 구성을 확인할 수 있다.
- 등록된 빌드 정보 수만큼 `Build Job`과 `Analysis Job` 미리보기가 생성된다.
- 미리보기에서 `Analysis Job`이 별도 checkout 흐름으로 표시된다.
- 미리보기에서 `Build Job` 산출물은 binary package, `Analysis Job` 산출물은 report로 표시된다.
- 실행 시작 API가 `buildKey`를 받아 저장할 수 있다.
- 동일한 플랜/빌드번호 조합이라도 `buildKey`가 다르면 서로 다른 실행으로 저장된다.
- 서버 테스트와 브라우저 E2E 테스트로 주요 UI/서비스 흐름이 검증된다.

## 제약/가정

- 현재 실행 종료와 정적 분석 결과 기록은 기존 실행 모델을 유지한다.
- `buildKey`가 없는 기존 실행 기록은 당분간 `미분류`로 볼 수 있다.
- 빌드 정보는 플랜 내부에서만 유일한 `buildKey`를 가진다.
- 현재는 빌드 정보 삭제 기능이 없어 수정/추가 중심으로 관리한다.
- Bamboo 구성 미리보기는 우선 활성 정의와 운영 UI 입력값을 결합한 예상 결과를 기준으로 한다.
- 외부 정의 동기화와 운영자 수동 수정이 충돌할 수 있으므로 override 정책은 별도 설계가 필요하다.
- Build/Analysis 분리 후에도 두 Job은 workspace를 공유하지 않는 것을 기본 가정으로 한다.

## 오픈 이슈

- Bamboo 실제 실행 시 `buildKey`를 어떤 단계/태스크 기준으로 전달할지 결정 필요
- 빌드키별 정적 분석 결과를 플랜 수준에서 어떻게 취합/표시할지 결정 필요
- 빌드 정보 삭제나 이름 변경 시 기존 실행 이력과의 연결 보존 정책 결정 필요
- `언어`, `컴파일러`를 자유 입력으로 둘지 추천 목록/검증 규칙을 더 강화할지 결정 필요
- 활성 정의 원본과 UI 수정값이 모두 존재할 때 어떤 값을 우선 적용할지 결정 필요
- Build Job과 Analysis Job의 단계 이름을 고정 템플릿으로 둘지 결정 필요
- Analysis Job report 포맷과 저장 위치를 어떻게 표준화할지 결정 필요

## 다음 단계

- 빌드 정보 삭제/비활성화 정책과 권한 모델을 정리한다.
- 빌드 상세에 예상 Bamboo Plan/Job 미리보기 패널과 수정 UX를 설계/구현한다.
- Build/Analysis 분리 구조에 맞춰 preview와 export draft를 재정렬한다.
