# STORY-28 빌드 플랜 대시보드 및 빌드 정보 관리 체계 정리

## 유형

- Story

## 구현 상태

- 부분 구현

## 우선순위

- 높음

## 요약

운영 콘솔은 프로젝트/저장소/빌드 플랜을 일관된 대시보드 경험으로 제공해야 하며, 빌드 플랜은 플랜 공통 메타데이터와 플랜 하위의 여러 `빌드 정보`를 구분해 관리할 수 있어야 한다.

## 배경

- 최근 운영 UI는 프로젝트 등록/조회에서 시작해 프로젝트 상세, 저장소 상세, 빌드 상세, 빌드 플랜 인덱스로 확장됐다.
- 초기 구현에서는 `빌드 정보`를 실행 이력처럼 다뤘지만, 실제 운영 요구는 Bamboo 플랜 아래 여러 종류의 빌드 환경구성을 별도로 관리하는 것이다.
- 하나의 Bamboo 플랜 안에서도 빌드가 여러 번, 여러 종류로 수행될 수 있으므로 플랜 공통 메타데이터와 개별 빌드 환경구성을 분리해야 한다.

## 설명

운영 콘솔 UI는 메인 대시보드와 상세 화면 사이의 시각적/동선적 괴리감이 없어야 한다. 상단 네비게이션 검색, 프로젝트 등록/수정 패널, 프로젝트/저장소/빌드 상세, 빌드 플랜 인덱스는 동일한 보드형 대시보드 언어를 사용해야 하며, 자동 스크롤이나 접힘/펼침 동작도 sticky 네비게이션 높이를 고려해 자연스럽게 동작해야 한다.

빌드 플랜은 공통 메타데이터와 개별 `빌드 정보`를 분리해서 관리한다. 플랜 공통 메타데이터는 `정적분석 도구 버전`, `Coverity Project`를 가진다. `빌드 정보`는 플랜 아래 여러 건 존재할 수 있으며, 각 항목은 실제 Bamboo 플랜 내부의 개별 빌드 단위를 대표한다. 이 항목은 `빌드키`, `pre process`, `빌드 명령어`, `클린 명령어`, `언어`, `컴파일러`, `분석 제외 파일`, `Coverity Stream`, `빌드 sub path`를 포함해야 한다.

실행 이력은 여전히 별도 데이터로 유지되지만, 앞으로는 실행 시작/종료 시 `buildKey`를 함께 전달해 어떤 `빌드 정보`에 해당하는 실행인지 구분할 수 있어야 한다. 이렇게 하면 같은 플랜 내 여러 빌드의 정적 분석 결과를 빌드키 기준으로 개별 집계하고, 이후 플랜 수준으로 취합할 수 있다.

## 범위

### 포함

- 메인 대시보드와 상세 페이지 간 공통 UI 패턴 정리
- 상단 검색, 접힘/펼침, 스크롤 보정, 부분 페이징 같은 운영 UX 정교화
- 빌드 플랜 인덱스 페이지 추가 및 네비게이션 연결
- 빌드 상세에서 플랜 공통 메타데이터 관리
- 플랜 하위 다건 `빌드 정보` 등록/조회/수정
- `빌드 정보` 전용 목록/상세 페이지
- 실행 시작 API에서 `buildKey`를 받을 수 있는 구조 정의
- 빌드키 기준 실행 결과 집계 방향 정의

### 제외

- 실제 Bamboo 잡에서 `buildKey` 전달 로직 구현
- 빌드 정보 삭제/비활성화 정책
- 빌드키별 정적 분석 결과의 최종 집계/리포트 화면
- 권한/감사 로그 상세 정책

## 요구사항

- 운영 콘솔 페이지들은 메인 대시보드와 시각 언어가 일관되어야 한다.
- 프로젝트 등록/수정, 저장소 추가, 빌드 추가 패널은 접힘/펼침 상태를 지원해야 한다.
- 자동 스크롤 이동은 sticky 네비게이션 높이를 고려해야 한다.
- 프로젝트 목록 페이징은 전체 페이지 리로드가 아니라 리스트 영역만 갱신할 수 있어야 한다.
- 상단 네비게이션 검색은 빈 입력에서는 결과를 노출하지 않아야 하며, 입력 문자열 포함 기준으로 프로젝트를 필터링해야 한다.
- 빌드 플랜은 `정적분석 도구 버전`, `Coverity Project`를 공통 메타데이터로 관리해야 한다.
- 하나의 빌드 플랜 아래 여러 `빌드 정보`를 등록할 수 있어야 한다.
- `빌드 정보`는 다음 필드를 가져야 한다.
  - `빌드키`
  - `pre process`
  - `빌드 명령어`
  - `클린 명령어`
  - `언어`
  - `컴파일러`
  - `분석 제외 파일`
  - `Coverity Stream`
  - `빌드 sub path`
- 실행 시작 API는 선택적으로 `buildKey`를 받을 수 있어야 한다.
- 같은 플랜에서 같은 `buildNumber`라도 서로 다른 `buildKey`면 별도 실행으로 기록할 수 있어야 한다.
- 빌드 정보 목록 화면은 등록된 빌드 환경구성과 현재 실행 집계 미리보기를 함께 보여줄 수 있어야 한다.

## 수용 기준

- `/build-plans/`에서 빌드 플랜 인덱스를 조회할 수 있다.
- 빌드 상세 화면에서 플랜 공통 메타데이터를 수정할 수 있다.
- `/projects/{jira}/builds/{planKey}/infos/`에서 빌드 정보를 등록/조회할 수 있다.
- `/projects/{jira}/builds/{planKey}/infos/{buildKey}/`에서 개별 빌드 정보를 수정할 수 있다.
- 빌드 정보 등록 후 목록/상세 화면에서 입력한 필드가 조회된다.
- 실행 시작 API가 `buildKey`를 받아 저장할 수 있다.
- 동일한 플랜/빌드번호 조합이라도 `buildKey`가 다르면 서로 다른 실행으로 저장된다.
- 서버 테스트와 브라우저 E2E 테스트로 주요 UI/서비스 흐름이 검증된다.

## 제약/가정

- 현재 실행 종료와 정적 분석 결과 기록은 기존 실행 모델을 유지한다.
- `buildKey`가 없는 기존 실행 기록은 당분간 `미분류`로 볼 수 있다.
- 빌드 정보는 플랜 내부에서만 유일한 `buildKey`를 가진다.
- 현재는 빌드 정보 삭제 기능이 없어 수정/추가 중심으로 관리한다.

## 오픈 이슈

- Bamboo 실제 실행 시 `buildKey`를 어떤 단계/태스크 기준으로 전달할지 결정 필요
- 빌드키별 정적 분석 결과를 플랜 수준에서 어떻게 취합/표시할지 결정 필요
- 빌드 정보 삭제나 이름 변경 시 기존 실행 이력과의 연결 보존 정책 결정 필요
- `언어`, `컴파일러`를 자유 입력으로 둘지 추천 목록/검증 규칙을 더 강화할지 결정 필요
