# CRS: 플랜 스크립트 자산 분리 및 환경별 커스터마이징 관리

## 문서 메타데이터

- 문서 일자: 2026-03-18
- 문서 유형: CRS
- 상태: 초안
- 대상 프로젝트: `bamboo_spec_generator`
- Jira 전환 대상: Story 초안

## 요약

Bamboo 플랜의 Task 실행 스크립트는 공통 로직과 빌드 환경별 차이를 분리해 관리할 수 있어야 한다. 공통적으로 재사용되는 스크립트 자산은 저장소에서 별도 파일로 관리해 수정과 배포가 쉬워야 하며, Specs 생성 시에는 대상 빌드 환경과 Task 특성에 맞게 필요한 값이 치환되거나 조합된 형태로 커스터마이징되어 최종 생성물에 반영되어야 한다. 또한 스크립트 형태의 Task는 스크립트 언어별로 `sh`, `bat`, `py` 등의 파일로 구분해 사람이 직접 읽고 편집하기 쉬운 방식으로 관리되어야 한다.

## 배경

- 현재 플랜 생성 로직은 공통 Task 실행 내용을 코드 내부 문자열로 직접 포함하는 구조에 가깝다.
- 실제 플랜 스크립트는 준비, 빌드, 정적 분석, 후속 작업 트리거 등 여러 단계에서 공통 패턴을 반복한다.
- 운영 중 공통 스크립트 로직을 수정하거나 배포할 때 코드 내부에 흩어진 문자열 방식은 변경 영향 파악과 재사용이 어렵다.
- 빌드 환경에 따라 OS, 셸, 컴파일러, 작업 경로, 호출 명령이 달라지므로 공통 자산만으로는 실제 실행 스크립트를 직접 표현하기 어렵다.
- 스크립트가 독립 파일로 존재하지 않으면 편집기 지원, diff 가독성, 재검토, 운영 표준화 측면에서 비효율이 크다.

## 문제

플랜 스크립트를 생성 코드 내부에 직접 박아 넣는 방식은 공통 로직 재사용과 변경 통제가 어렵다. 공통 스크립트 일부만 수정하려 해도 생성기 코드와 문자열 조합 로직을 함께 이해해야 하고, 빌드 환경별 차이를 안전하게 분리하기도 어렵다. 또한 Task가 본질적으로 스크립트 실행인 경우에도 언어별 파일 형태로 관리되지 않으면 검토, 편집, 테스트, 운영 이관이 불편해진다.

## 범위

### 포함 범위

- 플랜 Task 스크립트를 공통 자산과 환경별 가변 요소로 분리하는 관리 원칙 정의
- 공통 스크립트 자산의 저장소 내 관리 위치와 구성 방식 정의
- Specs 생성 시 공통 스크립트 자산을 환경별로 커스터마이징하는 방식 정의
- Task가 스크립트 형태인 경우 언어별 파일 확장자와 관리 단위 정의
- 사람이 직접 읽고 편집하기 쉬운 스크립트 관리 방침 정의
- 공통 스크립트 수정 후 생성 결과에 반영하는 배포 및 반영 흐름의 요구사항 정의

### 제외 범위

- 특정 템플릿 엔진 도입 확정
- Bamboo 서버에 스크립트 파일만 별도 배포하는 기능 구현
- 모든 스크립트 언어에 대한 문법 검증기 또는 실행기 내장
- 스크립트 편집용 별도 UI 제공

## 요구사항

### 기능 요구사항

- 시스템은 플랜 Task 스크립트에서 공통적으로 재사용되는 부분을 별도 스크립트 자산으로 관리할 수 있어야 한다.
- 시스템은 빌드 환경에 따라 달라지는 값과 로직을 공통 자산과 분리해 표현할 수 있어야 한다.
- 시스템은 Specs 생성 시 대상 빌드의 OS, 셸, 언어, 컴파일러, 작업 경로, 명령 구성에 맞춰 공통 스크립트 자산을 커스터마이징할 수 있어야 한다.
- 시스템은 준비, 빌드, 정적 분석, 후속 작업 등 여러 Task가 동일한 공통 스크립트 조각을 공유할 수 있도록 해야 한다.
- 시스템은 스크립트 형태의 Task를 스크립트 언어별 파일로 관리할 수 있어야 한다.
- 시스템은 최소한 `sh`, `bat`, `py` 형태의 파일 관리 방식을 지원 대상으로 고려해야 한다.
- 시스템은 언어별 스크립트 파일이 저장소에서 직접 열람, 수정, diff 검토가 가능하도록 평문 파일로 관리해야 한다.
- 시스템은 공통 스크립트 자산과 환경별 변수 정의 사이의 매핑 규칙을 문서화할 수 있어야 한다.
- 시스템은 공통 스크립트 변경 시 어떤 플랜 생성 결과에 영향이 있는지 추적 가능한 구조를 지향해야 한다.
- 시스템은 생성 결과에 포함되는 최종 스크립트가 실행 가능한 완성 형태가 되도록 공통부와 환경별 값의 결합 순서를 일관되게 유지해야 한다.

### 비기능 요구사항

- 공통 스크립트 자산은 수정과 재배포가 쉬운 디렉터리 구조를 가져야 한다.
- 동일 입력과 동일 스크립트 자산 버전에 대해 생성 결과는 일관되어야 한다.
- 스크립트 자산 구조는 편집기에서 일반 소스 파일처럼 다루기 쉬워야 한다.
- 스크립트 자산 관리 방식은 코드 내부 대형 문자열보다 검토와 유지보수에 유리해야 한다.
- 가능하면 공통 로직과 환경별 오버라이드를 명확히 구분해 변경 범위를 최소화할 수 있어야 한다.

## 수용 기준

- 플랜 Task 스크립트를 공통 자산과 환경별 커스터마이징 요소로 분리해 관리한다는 요구사항이 정의되어 있다.
- 공통 스크립트 자산이 저장소 내 별도 파일로 관리되어야 한다고 정의되어 있다.
- Specs 생성 시 대상 빌드 환경에 맞춰 최종 스크립트가 커스터마이징되어 반영된다고 정의되어 있다.
- 스크립트 형태의 Task가 언어별로 `sh`, `bat`, `py` 등의 파일 단위로 관리되어야 한다고 정의되어 있다.
- 스크립트 파일이 사람이 직접 편집하고 검토하기 쉬운 구조여야 한다고 정의되어 있다.
- 공통 스크립트 변경이 생성 결과 반영 흐름과 연결되도록 관리해야 한다고 정의되어 있다.

## 제약/가정

- 최종 Bamboo Specs 표현이 inline script인지, 저장소 내 파일 참조인지, 생성 시점 파일 내장 방식인지는 후속 설계에서 구체화가 필요하다.
- 초기 범위에서는 공통 자산 분리와 커스터마이징 원칙 정의에 집중하고, 세부 템플릿 문법은 후속 결정으로 둔다.
- 스크립트 언어 종류는 운영 환경에 따라 확대될 수 있으나 초기 요구사항은 `sh`, `bat`, `py`를 우선 대상으로 둔다.
- 빌드 환경별 차이는 최소한 OS, 셸, 컴파일러, 작업 경로, 실행 명령 차원을 포함한다고 가정한다.
- 공통 스크립트 자산의 배포는 생성기 저장소의 버전 관리와 생성 실행 절차를 통해 이뤄진다고 가정한다.

## 오픈 이슈

- 공통 스크립트 자산을 템플릿 파일로 볼지, 조합 가능한 조각 파일 집합으로 볼지 결정 필요
- 환경별 커스터마이징 범위를 변수 치환 중심으로 둘지, 조건 분기 허용 범위까지 열어둘지 결정 필요
- 최종 생성물에 스크립트 파일 자체를 남길지, Java 코드나 다른 산출물 안에 내장할지 결정 필요
- 스크립트 자산 디렉터리를 언어 기준으로 나눌지, Task 종류 기준으로 나눌지 결정 필요
- 공통 스크립트 변경 영향 범위를 검증할 자동 테스트 전략이 필요
