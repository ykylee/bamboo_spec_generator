# SRS: bamboo_spec_generator 통합 시스템 요구사항

## 문서 메타데이터

- 문서 일자: 2026-03-18
- 문서 유형: SRS
- 상태: 초안
- 대상 프로젝트: `bamboo_spec_generator`
- 관련 CRS: [./CRS.md](./CRS.md)
- 관련 이슈 분해: [./issues/BREAKDOWN.md](./issues/BREAKDOWN.md)

## 요약

본 시스템은 연도별 JSON 빌드 정의 또는 향후 DB에 저장된 활성 빌드 정의를 읽어 Bamboo Specs Java 코드를 생성하는 로컬 실행형 생성기에서 출발하지만, 장기적으로는 Bamboo 기반 CI/CD 전반을 관리하는 운영 시스템이어야 한다. 시스템은 공통 워크플로우, 저장소 연결, 브랜치 트리거, 스크립트 자산 렌더링, 작업 하위 경로, MSBuild 예외 처리, 빌드 결과 및 버전의 DB 관리, 배포 환경 및 릴리스 관리, 그리고 운영 백엔드/API/조회 UI를 함께 지원해야 한다.

## 구현 범위 구분

- 본 문서는 현재 구현과 향후 확장 요구를 함께 포함한다.
- 현재 구현 범위는 JSON 입력 처리, 공통 워크플로우 생성, 저장소 식별 정보 반영, 작업 하위 경로, MSBuild 보정용 스크립트 자산, 단일 Specs 프로젝트 출력, Django 운영 백엔드 스캐폴딩, 기본 Ninja API, 기본 조회 UI, SQLite/PostgreSQL 스위치, 개발용 DB 초기화 명령이다.
- 향후 확장 범위는 JSON 적재 자동화, 실제 운영 데이터 적재, 준비 스테이지 실연동, 동일 커밋 재빌드의 end-to-end 처리, 브랜치 트리거 생성, `create_if_missing` 세부 동작, 조회 UI 확장이다.

## 배경

- 빌드 플랜 수작업 구성은 반복 비용과 설정 편차를 유발한다.
- 입력 정의와 운영 메타데이터가 분리되지 않으면 버전 추적과 재빌드 처리가 어렵다.
- 공통 스크립트와 MSBuild 예외 처리, 저장소 연결 규칙은 제품 수준 공통 기능이다.

## 목표

- JSON 또는 DB 기반 정의를 단일 내부 모델로 변환한다.
- 공통 워크플로우를 유지하면서 빌드별 차이는 입력 데이터로 표현한다.
- 스크립트 자산, 작업 경로, MSBuild 보정 규칙을 일관되게 생성 결과에 반영한다.
- 빌드 결과와 버전 이력을 DB에서 추적 가능하게 한다.
- 빌드 이후 배포 단계와 환경별 릴리스 상태까지 같은 운영 시스템에서 관리 가능하게 한다.

## 비목표

- Bamboo 서버 자동 반영
- GUI 제공
- Bamboo 외 도구 지원
- DB 운영 세부 인프라 확정

## 사용자 및 사용 시나리오

### 사용자

- 빌드 엔지니어
- DevOps 담당자
- Bamboo 플랜 운영자
- 운영 메타데이터 조회 사용자

### 주요 사용 시나리오

1. 사용자가 `build_info_json/` 아래에 빌드 정의를 작성한다.
2. 생성기가 JSON 또는 DB에서 활성 빌드 정의를 조회한다.
3. 시스템이 입력을 검증하고 내부 모델로 변환한다.
4. 시스템이 스크립트 자산과 저장소 연결, 브랜치 트리거, 하위 경로, MSBuild 규칙을 반영해 Specs를 생성한다.
5. 빌드 준비 스테이지가 시작되면 프로젝트/저장소 메타데이터를 DB에서 읽어 변수로 등록한다.
6. 빌드가 실행되면 결과와 버전 정보를 DB에 저장한다.
7. 동일 커밋 재빌드 시 기존 버전 레코드를 재사용하고 실행 이력을 추가 저장한다.
8. 운영 사용자가 웹 화면에서 프로젝트, 플랜, 버전, 실행 이력을 조회한다.
9. 외부 연동 시스템이 Ninja API를 통해 프로젝트/플랜/실행 결과를 조회하거나 적재한다.
10. 운영 사용자가 특정 버전을 배포 후보로 승격하고 환경별 배포 상태를 확인한다.
11. 시스템이 환경별 배포 승인, 배포 완료, 배포 실패, 롤백 이력을 저장하고 조회한다.

## 기능 요구사항

### FR-01 입력 처리

- 시스템은 하나 이상의 JSON 파일 또는 입력 디렉터리를 처리할 수 있어야 한다.
- 시스템은 DB에서 활성 빌드 정의를 조회할 수 있어야 한다.
  - 현재 미구현
- 시스템은 파싱 실패와 검증 실패 시 대상 입력과 원인을 식별 가능하게 보고해야 한다.

### FR-02 연도별 관리

- 시스템은 입력 디렉터리 구조를 기준으로 연도를 해석할 수 있어야 한다.
- 시스템은 DB 기반 활성 빌드 정의를 사용할 때 연도를 별도 필드로 저장하고 조회할 수 있어야 한다.
- 동일 실행에서 여러 연도의 빌드 정의를 함께 처리할 수 있어야 한다.

### FR-03 빌드 정의 검증

- 시스템은 필수 필드 존재 여부를 검증해야 한다.
- 시스템은 중복 `buildId`, 중복 `planKey`, 필드 형식 오류를 검출해야 한다.
- 시스템은 저장소 브랜치 정책과 연결 모드 유효성을 검증해야 한다.
- 시스템은 하위 작업 경로가 저장소 내부 상대경로인지 검증해야 한다.

### FR-04 내부 모델 변환

- 시스템은 JSON 또는 DB 정의를 동일한 내부 모델로 변환해야 한다.
- 내부 모델은 연도, 빌드 식별자, 저장소 정보, 브랜치 정책, 빌드 상세 설정, 하위 작업 경로, 스크립트 렌더링 컨텍스트, 버전 메타데이터를 표현할 수 있어야 한다.
- JSON 입력에서는 디렉터리명에서 해석한 연도를 사용하고, DB 입력에서는 저장된 연도 필드를 사용해야 한다.

### FR-05 공통 워크플로우 생성

- 모든 생성 플랜은 동일한 워크플로우를 따라야 한다.
- 스테이지는 `Prepare`, `Build`, `Static Analysis`, `Trigger Follow-up`을 포함해야 한다.
- `Static Analysis`는 Coverity와 Custom Analysis 두 병렬 Job을 포함해야 한다.
- 커스텀 분석 명령 셋은 `analyze {build command}` 패턴을 포함해야 한다.

### FR-06 Bamboo Specs 생성

- 시스템은 내부 모델을 기반으로 Bamboo Specs Java 소스 코드를 생성해야 한다.
- 시스템은 여러 빌드를 하나의 Bamboo Specs 프로젝트 안에서 함께 생성해야 한다.
- 동일 입력에 대해 반복 실행 시 동일한 산출물을 생성해야 한다.

### FR-07 저장소 연결 및 브랜치 트리거

- 시스템은 `repository.projectKey`, `repository.repoSlug`로 Bitbucket 저장소를 식별해야 한다.
- 시스템은 `linked`, `create_if_missing` 연결 모드를 지원해야 한다.
  - 현재 구현은 `linkedRepositories(...)`와 plan-local `BitbucketServerRepository` 생성을 모두 지원한다.
- 시스템은 `create_if_missing`일 때 `repository.applicationLink`를 통해 Bamboo Application Link 이름을 제공받아야 한다.
- 시스템은 기본 브랜치 `dev`, `release`, `master`를 적용해야 한다.
- 시스템은 세 브랜치 각각에 대해 일관된 순서와 규칙으로 트리거 구성을 생성해야 한다.
  - 현재 Java Specs 생성에서는 `repositoryBranches(...)`, `planBranchManagement(...)`, `BitbucketServerTrigger`를 생성한다.

### FR-08 작업 하위 경로

- 시스템은 `subPath` 또는 동등한 작업 하위 경로 필드를 읽을 수 있어야 한다.
- 생략 시 저장소 루트를 기본 작업 위치로 사용해야 한다.
- 준비, 빌드, 정적분석 단계는 동일 작업 하위 경로를 기준으로 실행되어야 한다.
- 보조 파일 생성 위치도 동일 작업 경로 기준을 따라야 한다.

### FR-09 MSBuild 보정

- 시스템은 대상 빌드가 MSBuild 기반인지 식별할 수 있어야 한다.
- 시스템은 MSBuild 기반 플랜에서 실제 MSBuild 호출 직전에 `Directory.Build.targets`를 생성할 수 있어야 한다.
- 시스템은 Visual Studio 환경 설정 스크립트 경로를 기반으로 C++ 빌드 환경을 로드할 수 있어야 한다.

### FR-10 스크립트 자산 관리

- 시스템은 Task 스크립트를 코드 내부 대형 문자열이 아닌 별도 자산 파일로 관리할 수 있어야 한다.
- 시스템은 공통 자산, 프래그먼트, 오버레이를 조합해 최종 스크립트를 렌더링할 수 있어야 한다.
- 시스템은 최소한 `py`, `sh`, `bat` 자산을 관리 대상으로 고려해야 한다.
- 시스템은 렌더링 결과와 자산 출처를 추적 가능한 구조로 남길 수 있어야 한다.

### FR-11 빌드 정의 DB 저장

- 시스템은 현재 JSON으로 관리하는 빌드 정의를 DB에 적재할 수 있어야 한다.
- 시스템은 빌드 정의 스냅샷과 활성 정의를 구분해 관리할 수 있어야 한다.
- 시스템은 초기 전환 단계에서 JSON과 DB를 병행 검증하거나 순차 전환할 수 있어야 한다.
  - 현재 ORM 모델, migration, 활성 정의 구조와 관리 명령 기반 JSON 적재 경로는 구현되었지만 자동 동기화 경로는 미구현

### FR-12 프로젝트/저장소 메타데이터 조회 및 변수화

- 시스템은 빌드 준비 스테이지 시작 시 DB에서 프로젝트 단위 메타데이터를 조회할 수 있어야 한다.
- 시스템은 최소한 `jira project key`, `bitbucket project key`, `bitbucket repo slug`, `coverity project`, `coverity stream`, `대표 repo slug`를 조회할 수 있어야 한다.
- 시스템은 조회한 값을 빌드 준비 스테이지에서 사용할 변수로 등록할 수 있어야 한다.
- 시스템은 하나의 프로젝트 아래 여러 빌드 정의를 관리할 수 있어야 한다.
- 시스템은 하나의 프로젝트 아래 여러 저장소를 관리할 수 있어야 한다.
- 시스템은 결과 취합 시 프로젝트에 등록된 모든 저장소 정보를 조회 가능한 구조를 가져야 한다.
- 시스템은 현재 실행 중인 플랜이 프로젝트 내 어떤 빌드 항목에 대응하는지 식별할 수 있어야 한다.
  - 현재 Ninja API의 `prepare-context` 조회 경로와 selector 초안이 구현되었지만 실제 Bamboo 준비 스테이지 연동은 미구현

### FR-13 빌드 결과 저장

- 시스템은 각 빌드 플랜의 실행 결과를 플랜 단위로 정리해 저장할 수 있어야 한다.
- 시스템은 각 실행에 대해 최소한 실행 시각, 빌드 번호, 버전, 커밋 해시, 성공 여부, 결과 상태, 정적분석 결과, 요약 메시지를 저장할 수 있어야 한다.
- 시스템은 빌드 실패 시 실패한 스테이지, 잡, 가능하면 태스크를 저장할 수 있어야 한다.
  - 현재 백엔드 서비스와 API 초안이 구현되었지만 실제 외부 빌드 시스템 적재 연동은 미구현

### FR-14 버전 규칙

- 시스템은 버전을 `vX.X.X` 형식으로 관리해야 한다.
- `master` 빌드 시 major를 증가시키고 minor, patch를 `0`으로 초기화해야 한다.
- `release` 빌드 시 minor를 증가시키고 patch를 `0`으로 초기화해야 한다.
- `dev` 빌드 시 patch를 증가시켜야 한다.
  - 현재 백엔드 서비스 계층에서 초안 구현

### FR-15 최신 버전 및 재빌드 처리

- 시스템은 빌드 플랜별 최신 버전 포인터를 유지해야 한다.
- 시스템은 빌드 시작 시 `build_plan + commit_hash` 기준으로 기존 버전 레코드를 조회할 수 있어야 한다.
- 동일 커밋 재빌드 시 새 버전 생성 대신 기존 버전 레코드에 최신 결과를 갱신할 수 있어야 한다.
- 시스템은 브랜치가 달라도 같은 `build_plan + commit_hash` 조합에는 하나의 버전만 유지해야 하며, 중복 데이터가 존재하면 가장 높은 버전을 우선 재사용해야 한다.
- 시스템은 버전 레코드와 실행 이력을 분리해 관리할 수 있어야 한다.
  - 현재 백엔드 서비스 계층에서 초안 구현

### FR-16 생성기 연동

- 시스템은 생성기가 운영 백엔드의 Ninja API를 통해 활성 빌드 정의를 조회해 기존 생성 파이프라인에 사용할 수 있어야 한다.
- 입력 소스가 JSON이든 DB든 동일 내부 모델과 생성기 로직을 재사용할 수 있어야 한다.
- 시스템은 준비 스테이지에서 사용할 메타데이터 조회 결과를 Ninja API 응답을 통해 받아 스크립트 렌더링 컨텍스트 또는 실행 변수로 전달할 수 있어야 한다.
  - 현재 `--api-plan-key` 기반 활성 정의 조회와 API 클라이언트는 구현되었지만 prepare-context 연동은 미구현

### FR-17 운영 백엔드

- 시스템은 PostgreSQL을 영속 저장소로 사용하는 Django 기반 운영 백엔드를 제공할 수 있어야 한다.
- 운영 백엔드는 빌드 정의, 프로젝트, 저장소, 빌드 플랜, 버전, 실행 이력, 정적분석 결과를 관리할 수 있어야 한다.
- 운영 백엔드는 배포 환경, 릴리스 단위, 환경별 배포 실행, 승인/거절 이력을 관리할 수 있어야 한다.
- 운영 백엔드는 생성기 본체와 책임이 분리되어야 하며, 생성기와 독립 배포 가능해야 한다.
  - 현재 부분 구현

### FR-18 API

- 시스템은 Ninja 기반 HTTP API를 제공할 수 있어야 한다.
- API는 최소한 프로젝트 조회, 저장소 조회, 빌드 플랜 조회, 활성 빌드 정의 조회, 빌드 실행 결과 조회, 빌드 실행 결과 적재를 지원해야 한다.
- API는 환경별 배포 상태 조회, 릴리스 후보 조회, 배포 실행 결과 적재를 지원해야 한다.
- API는 준비 스테이지 변수 조회용 컨텍스트를 반환할 수 있어야 한다.
- 생성기는 보안상 DB 직접 연결 대신 이 API를 통해서만 운영 데이터를 조회해야 한다.
  - 현재 부분 구현

### FR-19 조회용 프론트엔드

- 시스템은 운영 사용자가 프로젝트, 저장소, 빌드 플랜, 최신 버전, 실행 이력, 정적분석 결과를 탐색할 수 있는 조회용 웹 프론트엔드를 제공할 수 있어야 한다.
- 시스템은 운영 사용자가 환경별 배포 상태, 최근 릴리스, 승인 대기 항목, 최근 실패 배포를 탐색할 수 있어야 한다.
- 초기 프론트엔드는 조회 중심 범위로 제한하고, 편집 기능은 후속 범위로 둘 수 있어야 한다.
  - 현재 프로젝트 목록/상세의 기본 Django 템플릿 화면만 부분 구현

### FR-20 배포 및 릴리스 관리

- 시스템은 빌드 결과를 배포 가능 아티팩트와 연결할 수 있어야 한다.
- 시스템은 배포 대상 환경(`dev`, `qa`, `staging`, `prod` 등)을 관리할 수 있어야 한다.
- 시스템은 릴리스 단위를 생성하고 해당 릴리스가 어떤 빌드 버전과 연관되는지 추적할 수 있어야 한다.
- 시스템은 환경별 배포 시도, 성공/실패 여부, 시작/종료 시각, 요청자, 승인자, 롤백 여부를 저장할 수 있어야 한다.
- 시스템은 환경별 현재 배포 버전과 직전 안정 버전을 조회할 수 있어야 한다.
- 시스템은 배포 실패 시 실패한 단계와 요약 메시지를 저장할 수 있어야 한다.

## 비기능 요구사항

### NFR-01 일관성

- 동일 입력과 동일 자산 버전에서 동일한 생성 결과를 보장해야 한다.
- 버전 계산 결과는 동일 조건에서 결정론적이어야 한다.

### NFR-02 유지보수성

- 파서, 검증기, 내부 모델, 생성기, 자산 렌더러, DB 접근 계층은 분리되어야 한다.
- 스크립트 자산은 평문 파일로 관리되어야 한다.
- 운영 백엔드, API, 프론트엔드는 생성기 본체와 책임이 분리되어야 한다.

### NFR-03 확장성

- 결과 저장 항목은 향후 추가 필드를 수용할 수 있어야 한다.
- 정적분석 결과는 요약에서 세부 지표로 확장 가능해야 한다.

### NFR-04 추적성

- 빌드 결과, 버전, 자산 출처, 정의 스냅샷은 운영자가 추적 가능해야 한다.

### NFR-05 마이그레이션 가능성

- JSON에서 DB로의 전환은 단계적으로 수행 가능해야 한다.
- Django/Ninja 계층 도입이 기존 JSON 기반 생성 흐름을 즉시 깨지 않아야 한다.

## 데이터 요구사항

- 입력 데이터: `buildId`, `planKey`, `repository`, `requirements`, `build`, `subPath`
- 프로젝트 메타데이터: `jiraProjectKey`, `bitbucketProjectKey`, `representativeRepoSlug`
- 저장소 메타데이터: `repoSlug`, `coverityProject`, `coverityStream`
- 빌드 그룹 메타데이터: 프로젝트 아래 여러 빌드 정의와 저장소 간 관계
- 운영 데이터: `buildNumber`, `version`, `commitHash`, `success`, `resultStatus`, `stage`, `job`, `task`
- 버전 데이터: `major`, `minor`, `patch`, `branchKind`, `isLatest`
- 정적분석 데이터: `toolName`, `status`, `summary`, 확장 가능한 세부 지표
- 배포 데이터: `environment`, `release`, `deploymentStatus`, `approvedBy`, `requestedBy`, `rollbackOf`, `deployedVersion`
- API 응답 데이터: 프로젝트 요약, 플랜 요약, 버전 요약, 실행 이력 목록, 준비 스테이지 변수 컨텍스트, 배포 상태 요약

## 시스템 인터페이스

- 입력 인터페이스: CLI, 파일 입력, DB 조회, Ninja API
- 출력 인터페이스: Bamboo Specs 프로젝트, 스크립트 번들, 비교/요약 리포트, 버전/결과 메타데이터, 조회용 웹 UI

## 수용 기준

- 생성, 저장소 연결, 브랜치 트리거, 스크립트 자산, 작업 하위 경로, MSBuild 보정, DB 메타데이터 요구가 하나의 문서에 통합되어 있다.
- 버전 규칙과 동일 커밋 재빌드 처리 규칙이 명확히 정의되어 있다.
- 생성기에서 DB 기반 입력으로 전환하는 방향이 정의되어 있다.
- Django 기반 운영 백엔드, Ninja API, 조회용 프론트엔드 요구가 정의되어 있다.
